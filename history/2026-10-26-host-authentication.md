# 两个宿主接入认证业务链路

日期：2026-10-26。对应 [04 §7.2](../04-wire-protocol.md)、[17 §5](../17-storage-and-config.md)、
[ADR-017](../20-adr.md)，当前任务状态以 [19 D1、D2](../19-roadmap.md) 为准。

## 生产入口变化

共享 `initialize_native_network` 要求文件数据库，使用 `synra/device-identity` 服务命名空间。
Windows 从原生凭据后端恢复或登记本机密钥，已有登记不换钥；未实现原生后端的平台返回不可用。
daemon 启动和应用 listener 绑定阶段均调用此服务，失败时保留本地工作能力，网络配置记录拒绝原因。

`Host` 初始没有可用的认证配置；`DialConfig` 克隆配置和当前 profile，网络工作在 Host 锁外执行。
出站按目标设备 id 查询当前凭据授权，先批准后打开 TCP，地址不代替身份；入站 TLS 和 Hello 完成后才持锁记录 session。
`Dialled` 直接保留带授权检查的 `PeerLink`，不能通过重新包装 socket 或改变 local id 丢失授权代次。
发送文本、文件、同步、意图、旧配对命令的拨号及晚到应答均已切换到此路径，旧 token 不参与认证。
按裸地址发送文件的旧分支被移除，必须先解析要通信的设备身份。

共享 listener 的后续帧仍由已捕获代次的链路授权检查保护，撤销与存储失败分别记录为 `authorization` 和 `authorization_storage`，
不能把它们记成普通协议格式错误。未完成认证不创建 session，也不会发送业务帧或退回普通 TCP。

## 验证

核心 Host 的 33 个测试使用真实文件数据库与实际证书，包括原有通信和生命周期测试迁移到 TLS，
新增默认未配置拒绝、撤销后在打开 socket 前拒绝；测试中推进 session 时钟不再错误地沿用旧固定 epoch。

原生启动新增两项验证：内存库在登记前被拒绝；Windows 真实后端两次初始化复用同一证书，
删除原生密钥后第三次初始化失败，数据库公开登记保持原样，不自动替换身份。

daemon 的 11 个传输测试经过生产共享 listener 和真实 TLS，新增撤销后业务帧不被分发且记录授权拒绝指标，
以及 TLS 已完成但对端尚未发送 Hello 时仍能取得 Host 锁。
两项文件与插件包完整接收测试也迁移到凭据授权和 TLS，移除只提供裸地址、不指定身份的旧夹具，保留完成与指标断言。
应用新增两个真实拨号测试：生产意图交付入口在 TLS 和 Hello 后发送并接收关联应答；
只恢复设备列表和旧 token 时无法恢复凭据授权，且不打开 TCP。

共享测试夹具在 `synra-testkit::authentication` 中，明确预置已批准的公开信任事实，
不写 OS keychain，也不将预置授权当成首次配对协议或原生私钥持久性的证据；后两者由各自的生产流程测试承担。

阶段门禁通过：工作区测试（含集成测试与 doctest）、全部目标 lint、所有修改 Rust 文件格式检查、
12 项架构守卫（含工作区 Rust 1.88、应用调用方和 93 份文档链接检查），应用默认 Tauri 编译、319 个 Rust 测试及全部目标 lint。
首次全量测试在 daemon 两个旧地址夹具处中断，已通过的包不重复运行；迁移后定向重跑两项完整传输测试、
新增锁范围测试，并补齐未运行的 workspace 包及全量 doctest，最后复核受影响的 daemon lint。
Android 核心库编译通过，没有运行结果；该平台生产初始化仍明确返回原生后端不可用。
本轮未修改前端，未重复执行前端构建与测试，也未做性能基准或发版工作。
最终格式复核发现同一工具链对嵌套 JSON 宏与闭包链的第二次排版仍有变化，改为先绑定错误参数值，确保格式检查稳定；
修正后定向复核应用传输模块与 lint，不重复未受影响的完整检查。

## 接入中确认的未完成事项

首次配对的可信带外邀请、受限通道与双方完成确认已有共享实现，但产品入口仍未接入。
原用户配对命令不能再凭公开六位码、metadata 或 token 给未批准身份授权，缺少新绑定时会被拒绝；
需要把首次配对入口整体改为受限配对流程，不能通过放开业务 TLS 或自动信任旧 token 恢复旧行为。
Android 等平台原生后端尚未实现，因此该平台当前拒绝生产联网；跨编译不等于设备运行验证。
显式身份修复与重配、真实取消和平台恢复仍需覆盖，D1 保持开发中。

检查应用 `commands::transfers::send_ready_since` 时，确认它目前只调用低层 `transfer::send_blocks`，
没有调用共享 session 层的提议、完成与接收端确认流程；原成功测试也只验证内存链路收到块。
这不能证明真实 listener 能完成文件接收，更不能将块写入 socket 当成已交付成功；本轮认证验证不作此结论。
后续 D2 应复用完整共享发送流程、保留进度与取消语义，并以生产接收端验证结果和失败状态。
本记录将该缺口列为待开发，不把原来内存测试通过视为完成证据。
