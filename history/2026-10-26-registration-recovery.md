# 公开登记与身份元数据丢失恢复

日期：2026-10-26。对应 [19 §0.2 D1](../19-roadmap.md)、[17 §5](../17-storage-and-config.md) 和 [08 §1](../08-ipc-and-frontend.md)。

## 问题与契约

原先在没有配对元数据时，删除 device_credentials 会重新打开初次登记入口；
删除 identity 也会让下一次启动生成另一设备 id，无法区分首次启动与记录丢失。
现有显式修复又要求活动登记存在，无法确认和修复这两种丢失。

schema 22 独立保留 device_identity_history：稳定设备 id、最近登记的公开证书和后端。
它不随 identity 级联删除，没有私钥，不参与网络授权，也不能把凭据标成 ready。
identity_bootstrap 独立记录是否初始化过，并拒绝删除和复位；
初次身份创建在短 SQLite 写事务中读取这些事实，两个真实连接竞争时仅有一个赢家。
首次登记只有在沿革尚无证书且不存在授权、配对元数据、配对任务和退休密钥时才能成功，
活动登记与沿革在一个事务内写入，不存在删除活动登记即可重新生成密钥的分支。

身份元数据丢失时从沿革恢复相同设备 id，显示名称和平台按本次默认值重建，不声称恢复原名称。
资料更新仅允许同一 device id，并通过条件 UPDATE 拒绝行被删除或身份变化的竞态；
测试夹具必须首次创建指定身份，不能依赖资料更新来改 id。
身份和沿革同时丢失则拒绝创建，要求可信数据库备份；
本轮不覆盖整个数据库文件丢失、跨设备导入或平台迁移。

## 显式恢复与清理

CredentialSnapshot 的 enrollment 仍只表示实际活动登记；丢失时 recovery 提供独立的公开指纹和后端，
没有 ready 字段，不证明私钥可用或曾经批准过某个对端。
共享登记和加载服务拒绝自动生成替代密钥；修复要求用户确认此指纹。
若活动登记仍在而沿革丢失，也仅能在明确修复的事务内以该登记重新建立沿革。

修复在同一 FULL/WAL 事务中比较原指纹对应的公开记录、更新沿革、写入未就绪登记、
记录旧密钥清理任务并撤销全部授权、配对列表及待处理配对，然后在数据库锁外写入新私钥。
失败前后状态继续遵守既有写入读回契约，重启只能恢复同一已提交的新钥，不生成第三把钥匙。
失效确认和跨连接竞争拒绝；清理同时检查活动登记和恢复沿革，不能删除仍被任一引用的槽位。
原有跨进程 OS 文件锁与退休队列容量限制继续生效。

应用和 daemon 均使用共享恢复服务；设置页明确显示登记丢失，确认框固定用户审阅的原指纹。
活动登记和沿革同时缺失时，应用以独立本地化消息说明可信备份要求。
新钥提交、旧密钥清理和进程身份继续分别报告，成功后需重启并重新配对；
保留的沿革不会使现有或旧连接重新获得权限。

## 验证

核心定向测试通过后执行受影响包完整测试：core 811、store 286、protocol 244、IPC 123、
daemon 256 项单测及其集成测试和 doctest 全部通过，五个包全部目标 Clippy 通过。
API 守卫 25 项及稳定性检查 3 项通过。
收尾补充分辨从未登记与登记丢失的错误断言后，定向复核 23 项凭据单测及子进程验证、core 全部目标 Clippy，复用未受影响的全量结果。
发现用例夹具原先依赖修改稳定 id 后，改为首次创建指定身份；两处发现模块保留未改动的历史格式，仅对新夹具片段检查格式。
存储测试覆盖元数据恢复、双记录丢失拒绝、首次身份并发、禁止修改稳定 id、原子撤销、
事务失败回滚、沿革恢复和清理保护。
核心测试覆盖写入前失败、写入后报错、损坏、丢写及重启，不允许因活动登记再次丢失而自动生成第三把钥匙。
真实 TLS 双端测试同时覆盖普通修复与登记丢失恢复，验证旧连接持续拒绝、新配对仅允许新连接。

原生命令使用真实文件数据库和 Windows Credential Manager；daemon 通过生产状态与修复入口、
独立连接删除 identity、恢复相同 id，以及原生网络重启读回新钥。
前端先完成 345 项全量测试，新增备份提示后定向组件与 store 共 7 项通过，
复用未受影响结果覆盖当前 346 项。
JS 四组测试共 194 项通过，并通过类型、消费者、形状、文档类型与全量 lint。
前端全量 lint 通过后新增消息与测试按影响范围复核，类型及生产构建通过，应用 8 项形状守卫通过。
