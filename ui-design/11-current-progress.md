### 14.2 附近设备重复条目的根因（内核，非 UI）

上一批把 19 项记为“疑似同一主机多接口各报一次”，**这个判断是错的**。经 CDP 读取运行中的 `synra-app.exe`（`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port`），拿到的是内核答给页面的原始快照：

- 共 21 张卡片：19 个 UUIDv7 ＋ 2 个测试常量 `1111…-1111…`、`2222…-2222…`（后者来自网络上仍在广播的测试实例）。
- 19 个 UUIDv7 的创建时刻落在 10-16 至 10-19，**成对出现**（如 03:37:50.386 与 .762），相邻两张相差约 300–400 ms，说明每次运行产生了两个新身份。
- 所有卡片的 `lastSeenMs` 距今 **96–106 万秒（11–12 天）**。

**根因**（**这段写的是当时的情况，现在的代码已不是这样，见 16.54**）：`devices_snapshot` 走的是 `db.seen_devices()`（持久化表），**没有经过内存发现表的 `is_current` 过滤**。`DiscoveryTable::displayable` 确实按 `CANDIDATE_TTL = 90s` 过滤，但那套 TTL 只作用于内存候选；数据库这条路径从不检查年龄，于是 11 天前的记录一直显示，并标为“可连接”。

这不是 UI 缺陷，界面如实呈现了内核给的列表。修复应在内核：`seen_devices` 的读取要带同样的年龄判据，或写入时清理过期行。**本轮未改内核**。

**现状（16.54）**：候选列表读 `host.discovery().displayable(now)`，`is_current(now, ttl)` 就在其中；`db.seen_devices()` 现在只剩测试在用。**我无法断定是"当时看错了"还是"后来改了"**——两种都可能，代码里没有留下能判断这一点的痕迹。

### 15.2 F 要求的“测量后决定虚拟化” —— 结论是不做

F 的验收里有一句“测量后决定虚拟化/分页”。补上这个结论，以及得出它的依据。

**测不出渲染耗时，是工具限制，不是回避**：BSK 不提供任意 JS 注入，`--remote-debugging-port` 在本机拿不到，`debug performance` 要先开 capture 而页面已加载完。所以没有拿到“N 条列表渲染 X ms”的数字。

**但这个问题不需要那个数字就能答**。三个既有事实比一个耗时曲线更能定性：

1. **插件数量没有上限**（内核无 `MAX_PLUGINS` 一类常量），但一次安装需要用户显式确认，本机真实数据是 **2 个**。它是"用户主动攒出来的个位数到几十"，不是"随时间自动增长的流"。
2. ~~**设备库确实会无限增长，但这正是缺陷本身**~~：**这条已不成立，见 16.54。** 当时记的是「`forget_seen_devices_beyond(keep)` 生产代码零调用（全仓搜过，只有定义处和测试）」——**现在全仓能搜到生产调用**：清理走 `collect_loop → intents::sweep → forget_seen_devices_beyond(500)`，列表读的是内存发现表且过 `is_current(now, ttl)`。**是当时搜漏了、还是后来接上的，我判断不了**；能确定的是"全仓搜过"这个说法不该被当成永久结论——**它只对搜索那一刻的代码成立**。
3. **本来就可能有大量行的列表都已经分页**：审计是 20 条一页、注册表搜索是服务器分页、日志按点击读取且受字节预算约束（`07`、`08`）。

**结论**：现在加虚拟化，等于给一个"本不该有 19 条陈旧记录"的列表装上更顺滑的滚动——治的是症状。真要治，改的是 `seen_devices` 的读取与清理，不是前端渲染方式。虚拟化没有列入本批，也不是后续必须项；等某类列表真的出现用户攒到数百条的场景再说。

这块**没有产生代码改动**，只有这个判断。

**上一版这里写错了**：说首页候选选择/拒绝"没有被实测"。实际它有**两条完整的行为测试**，比渲染预览更强——断言的是点击后发出的命令与参数，不只是画面上有按钮：

- `lets the user accept an intent on a candidate device`：给一条 `state: 'choosing'`、带一个候选的 intent，断言 Accept 按钮存在，点击后 `intent_decide` 收到 `{ decision: 'accept', deviceId: <候选的 id> }`。
- `lets the user decline an intent while it is still matching`：给 `state: 'matching'`、无候选的 intent，断言 Decline 仍可用（旧规则把它绑在"有候选"上，导致匹配中的分享无任何动作可做），点击后 `intent_decide` 收到 `{ decision: 'decline', reason: null }`。

浏览器预览里看不到这一块，是因为假内核的 `INTENT` fixture 是 `state: 'succeeded'` 且 `candidates: []`——**不是因为能力缺失，也不是因为缺真机**。本轮没有改那个 fixture：它是开发展示数据，且这两条测试已经覆盖了要验的东西。

**25 项全部有下落，没有一项是"没验过"。**其中 24 项在真实浏览器页面上逐一看到，候选决策两项由行为测试覆盖。

### 16.5 200% 缩放：rail 形态正常，但差点误报一个假缺陷

### 16.6 弹层关闭后的焦点归还：代码路径成立，但我没能实测出来

`10 §6` 弹层维度有一条"焦点归还"，`04 §4.1` 也要求没有不可见的焦点目标。

**先查了实现的三种可能**：

1. 插件页 `closeRemoval()` 只写 `removing.value = undefined`，**没有显式 `.focus()`**——第一眼像是漏了。
2. 但 `@synra/theme` 里另外三处（PairingPanel、SearchPalette、TransferPrompt）都显式写了焦点转移，说明这个项目在意这件事。
3. 关键在 `node_modules/ant-design-vue/es/vc-dialog/Dialog.js:58`：

```js
if (props.mask && lastOutSideActiveElementRef.value && props.focusTriggerAfterClose) {
  lastOutSideActiveElementRef.value.focus({ preventScroll: true });
```

antd 打开弹层时会记下 `document.activeElement`，关闭时**默认归还**（`focusTriggerAfterClose` 默认 true）。所以 `closeRemoval()` 不写 `.focus()` 是**对的**——手写反而会覆盖记录值。这也解释了为什么其他三处会写：它们不是 Modal，是自定义面板。

**但我没能把这一步实测出来**：尝试了 Escape 后截图看 Remove 按钮有没有焦点环、Tab 判断落点，都没得到确定结论。焦点环又依赖 `:focus-visible`，鼠标点击触发的归还**不显示环**。

关于组合键，本批又试了一次：`bsk_interact press` 的 `modifiers` 字段按工具说明只作用于 hover 和 wheel，`press` 实际只发了单个 Tab。要想验证 Shift+Tab，得靠别的手段。

**结论**：按 antd 源码路径判断应当正常，但没有实测证据。这条标为"代码确认、未实测"，不写成通过。**这不是缺陷报告，是能力边界的记录**——下一个有真机的人可以用一次 Tab 确认它。

### 16.7 切换语言不丢草稿（实测通过）

`10 §6` 语言维度那条的原文是"打开弹层时切换语言且不丢草稿"。**弹层开着时够不到设置页**，所以按字面测不了。取它真正要保的性质：**界面上有一份没保存的输入时，换语言不能把它冲掉**。设置页的名称草稿正好是这个场景。

实测步骤与结果：

1. 「通用 › 名称」点「修改名称」，输入 `DraftName123`——页顶出现「有未保存的修改」。
2. 语言选 English。
3. 结果：整页文案切成英文（Settings / General / Language / Launch at login…），**输入框里仍是 `DraftName123`**，页顶仍是「Unsaved changes」，按钮变成 Save / Cancel。

也就是说语言切换只换文案，不动组件状态——因为语言是响应式的 `messages`，不是重建页面。证据见 `evidence/2026-10-30-states/05`。

**顺带一个观察**：切到英文后，「语言」下面多出一行小字 `Saved`，中文界面下没有。这是"语言已保存"的确认，本身合理，但中英不一致——记在这里，没改。它不是缺陷，是文案覆盖的差别。

### 16.8 任务详情：补上 `05 §5` 要求的那一半

走完整旅程时发现的真缺口。`05 §5` 写的是：

> `01HQ00000000000000000TRACE1` 不必永远展开整行，但**必须能在详情完整读取与复制**；复制只复制实际值，不包含"调用记录"标签。

而 `05 §3` 的表格把任务行分成两栏：常显（状态、插件标识、重试摘要）和详情（trace、开始时间、候选、错误）。**实现里只有常显那一栏**——trace 平铺在行上，没有开始时间，也没有任何复制手段。

**改法（用户选定"行内可展开"）**：行尾加一个「详情」披露按钮，展开后两行——`Started 08:00 AM` 和 `Trace 01HQ…` 加一个 Copy 按钮。trace 因此从常显移到了详情里，这也正是 §5 说的"不必永远展开整行"。

实测（fake kernel，`startedAtMs: 0`）：

- 折叠态：`Done @synra-plugin/github` + `Details`，看不到 trace
- 展开态：`Started 08:00 AM` / `Trace 01HQ00000000000000000TRACE1 [Copy]`
- 点 Copy 后读**系统剪贴板**：内容正是 `01HQ00000000000000000TRACE1`，**不带 "Trace" 前缀**——§5 那句"复制只复制实际值"落实了

证据见 `evidence/2026-10-30-task-detail/`（`01` 展开、`02` 折叠）。

**过程中修掉两个自己引入的问题**：

1. `v-if="intent.startedAtMs"` 把 `startedAtMs: 0` 当成"没有"（`0` 是假值），整行时间被吞掉。改成 `!== undefined`。这不是假内核的怪癖——`0` 是合法时间戳，真实内核也可能给出。
2. 「详情」按钮一开始渲染成一块灰方块、文字被压成 "etail"——原生 `<button>` 继承了 antd 的按钮底色。补 `border-0 bg-transparent` 后变成纯文本样式。

**一处没做**：详情里还该有"候选"和"错误详情"。候选本来就在行上（有设备可选的按钮），错误也在行上（`intentError`），所以详情里没有重复放。§3 把它们列在详情栏，但重复展示同一件事不比放在一处更好——这是判断，不是遗漏。

### 16.9 `05 §3` 那张五行表逐行核对

上一条只查了"任务"这一行。把整张表过一遍：

| 区域 | 默认栏 | 结论 |
| --- | --- | --- |
| 连接摘要 | 短线、名称、一个状态 | 齐 |
| 待处理 | 来源、等待原因、操作 | 齐（`TransferPrompt`） |
| 进行中传输 | 对端、文件、方向、进度、取消 | 齐；"点击后完整 ID"**没做**，见下 |
| 任务 | 状态、插件、重试摘要 | **补了详情**（`16.8`） |
| 接收记录 | 文件名、大小、**接收时间** | **接收时间一直没显示**，本轮补上 |

**接收记录缺的那一项**：`ReceivedFile.receivedAtMs` 从 DTO 第一版就有，注释写着"最后写入时刻"，但行里只渲染了名字、路径、字节数。一个人能看出文件到了，看不出什么时候到的。补一行 `Received 2026/10/30 12:05:06`，`title` 同值；`§5` 要求"开始时间不能被标成完成时间"，所以标签用 received 而不是 started。

**没做的一件事，以及为什么**：`§39` 说进行中传输"点击后"要看完整 ID 和字节数原因。字节数和进度已经在行上了，完整 ID 确实没有。但再给这一行加一个披露按钮，就没有一行的点击行为是"打开对象本身"了——四行各挂一个 Details，界面会被按钮填满。`§5` 只对 trace 明确要求"必须能在详情完整读取与复制"，传输的 transferId 没有同样的硬要求。**留在这里，不假装做过。**

**验证方式的诚实说明**：接收记录这一项**只有测试证据，没有浏览器截图**。假内核的 `transfer_received` 固定返回 `[]`，注释写着"空收件箱是全新安装的常见情况"——那是刻意的空状态，为了看效果去改它，等于把真实场景换成假数据。测试断言了文件名、路径、`2.0 KiB`、以及"显示的是格式化时间而不是 epoch 毫秒"。

**紧接着又发现同类问题：路径被截断**。`fileName` 和 `path` 都用了 `truncate`，长路径右侧直接省略号。`§5` 说的是"长标识允许换行或截断后**在详情完整展示**"——但接收记录没有详情，**截断就等于丢失**，而这恰恰是用户打开文件唯一要的东西。

改法：路径去掉 `truncate`，换 `break-all` + `title`。文件名保留 `truncate` 但补 `title`——文件名通常短，路径才是会长的那个。

**这里我差点重犯一个错误**：想临时改假内核造一条数据看布局，然后还原。上一条我刚写过"为看效果改夹具等于用假数据替换真实场景"，隔了几分钟又在做同一件事。停下来了。理由是：`break-all` 在项目里已经用了 24 处，配合父级 `min-w-0` 就是为长字符串准备的标准组合——**不是在猜一个新写法**。这一项因此是"测试断言 + 既有模式"，没有截图。

测试也加强了：原来用短路径，测不出截断；现在用一条长路径，并且断言的是 **class 列表里没有 `truncate`**（`text()` 返回完整字符串，测不出 CSS 裁剪），加上 `title` 等于完整路径。

### 16.10 同一类问题的第二处：发布者指纹被截断

接着查"哪些 `truncate` 后面拿不到完整值"。共 13 处，逐个判断后只有一处是真问题：

**发布者指纹**。`07 §104` 原文是：

> 发布者管理中显示 publisherId、指纹、信任状态与显式动作；**指纹可换行/复制，不只显示不可核对的前后几个字符**。

这句话几乎是在描述当时的实现：`truncate` 只显示前若干字符，**不可核对**。而指纹存在的唯一理由就是拿它跟别处给的指纹比对——截断后这个动作无法完成。旁边"信任"按钮传出去的却是**完整指纹**，说明完整值本该是依据。

改法与接收记录的路径一致：去 `truncate`，换 `break-all` + `title`；`publisherId` 保留 `truncate` 但补 `title`（它是标识，旁边有信任状态兜底）。顺手给指纹加 `select-text`，因为原文写着"可换行/复制"。

**没做的部分**：「复制」按钮。原文写"可换行/复制"，换行已经做了，选中文字就能复制（`select-text` 保证可选中），但页面上没有一键复制按钮。加一个要新文案、新状态、新测试，而 §104 用"/"连接两个选项，读作"任一种可达即可"。记在这里，不是遗漏。

**另外 12 处 `truncate` 的判断**（都不改，理由各不同）：`peerName`、`displayName`、`platform`、`version` 是短标识且用户可改；`SearchPalette` 的 `item.label` 是页面名，标题旁就是它的全称；`SettingsDiagnostics` 的 `seriesKey` 是图表序列的短键；`HomePage` 传输行的 `fileName` 在行内仍可读到完整值所在的那次传输。

**验证方式**：假内核的 `plugins_publishers` 固定返回 `[]`，是刻意的空状态，所以**只有测试证据，没有截图**。测试断言指纹 span 的 class 里没有 `truncate`、且 `title` 是完整值。原来那条测试用的是 `AB12 CD34 EF56 7890`——短到截不截断都过，**测不出问题**，现在补了 class 断言。

### 16.11 反查：该截断的有没有没截断，以及一处漏掉的 `title`

上两条查的是"截断后拿不到完整值"，这条反过来查"有没有该约束却没约束的长内容"。

**结果：没有溢出风险。** 唯一看着可疑的 `plugin.description` 是 `<p>` 里的自由文本，`<p>` 自带换行，不会撑破；其余候选（`pluginId`、`version`、`publisher`）都在已有的 `truncate`/`break` 约束下。

**但反查时发现另一件事**：`HomePage` 候选行的 `deviceId` 被父级 `truncate` 截断，且**没有 `title`**。单看像是"deviceId 只是辅助信息，截了无所谓"——因为旁边有 `deviceName`。

问题在 `deviceName` 的实现：

```ts
function deviceName(deviceId: string): string {
  return devices.byId.get(deviceId)?.displayName ?? deviceId
}
```

**设备不在 store 里时它回退成 deviceId 本身。** 也就是说，一台未登记的候选设备，那一行里**唯一的文字就是这段 UUID**，而它正好被截断。两台同名设备也只能靠这段 id 区分，同样被截断。

补 `title` 就够了——截断保留（行不该被长 id 撑开），但完整值随时可取。测试断言 `title` 等于完整 deviceId。假内核的候选数据来自 `INTENT`，那个 fixture 的 `candidates` 是空数组，所以这一行同样**只有测试证据，没有截图**。

### 16.12 `08` 设置与系统面：三处核对

换一种查法——`05`（首页）那条线查完了，改看 `08` 整章。九节里挑了三处容易"写了但没做"的：

**§3 切分类时的草稿（通过）**。原文要求"暂存在当前会话""真正离开设置时提供保存/放弃选择，不能静默丢失或偷偷提交"。实现是 `v-show` 切分类（内容不卸载，草稿天然保住）加 `onBeforeRouteLeave`（`leaveOpen` 弹层，`saveAndLeave` 走保存后离开，`resolveLeave(false)` 走放弃/取消）。**两半都在**。

**§7 通知跳转插件详情（通过）**。原文要求"真正打开目标详情，不只把插件页滚到顶"。`NoticeHost` 走 `?plugin=`，插件页的 `targetPluginId` 接住，测试覆盖了新进入、同页切换、目标不存在三种情况。

**§6 指标"不支持"与"为空"（第 31 轮更正：已满足）**。原文："指标不支持与指标为空分开"。第一次查时我写的是"判断不了"，理由是 `MetricsSnapshot` DTO 没有"不支持"字段、指标文案里也没有这一类。**那个结论是偷懒的**——我只在指标这一块找，没看通用的错误表达。第 31 轮补查：

- 项目里本来就有 `unsupported` 错误码（`errors.ts` 的 `unsupported(feature)`，`code: 'unsupported'`）
- 文案也有：`error.unsupported` = "This version cannot do that yet." / "此版本暂不支持这项操作。"
- `SettingsFeedback` 把 `errors.metrics` 交给 `ErrorNotice`，后者按 `code` 渲染

所以两条路是分开的：**内核回 `unsupported` → 错误提示说"暂不支持"；内核回空 `values` → 空状态说"还没记录过指标"**。DTO 里不需要"不支持"字段，因为那本来就不是数据，是一次调用失败。

**这是这几轮里唯一一次"我判断不了"其实是我没查全。** 教训具体：找一条通用原则（这里是 `04 §6` 的"功能未支持→当前区域说明不可用"）的实现时，不要只在出问题的那一块找。

### 16.13 `08 §8` 插件"打开"：三件事，两件有证据、一件不在范围

`08` 九节里最后一节没碰过的是 §8 托盘与独立插件窗口。其中可查的是这句：

> 插件详情"打开"指向独立 WebView；**打开中显示 busy，失败留可理解的原因**，已有窗口应聚焦原窗口。

**busy 有了**：`PluginsPage` 的打开按钮 `:loading="operations.busy.get(plugin.pluginId) === 'open'"`，同时 `:disabled` 防重复点击。

**失败原因有了**：`open()` 把 `answer.error` 的 `code/message/actions` 放进页面级 `error`，由 `ErrorNotice` 翻成句子并给恢复入口——和插件页其他操作同一条路径，不是只弹一句"打开失败"。

**第三条（已有窗口聚焦）不在这个仓库**：那是 `plugin_ui_open` 的内核行为，前端只发命令。文档里写明。

**验证覆盖**：`plugin-page.mount.test.ts` 有两条——`hasUi: true` 时按钮出现且点击发出 `plugin_ui_open`，`hasUi: false` 时按钮不出现。这条比前几轮的截断修复更硬：它验的是"命令有没有被调用"，不是"文字有没有被渲染"。

**没能在浏览器验**：假内核两个插件都是 `hasUi: false`，所以预览里这个按钮**根本不渲染**；`plugin_ui_open` 也不在假内核的命令表里。这一次不是"空列表"，是"控件不存在"——同样属于刻意的预览边界，不为看效果改夹具。

### 16.14 `04` 交互模式：三条可扫的查完了

`04` 有八节，挑出能用代码或扫描验证的三条：

**§4.3 hover/focus 不得触发动作（通过）**。原文点名的动作——授权、启动插件、检查更新、扫描、写配置、取消传输——都不得由 hover/focus 自动执行。全项目扫下来 `@mouseenter`/`@mouseover`/`@focus` 只有**一处**：`SearchPalette` 的 `activeId = item.id`，那是高亮当前项，不是动作。**没有任何动作挂在 hover 或 focus 上。**

### 16.15 `03 §4` 滚动职责：父子链对了，窄屏也不横溢

`03` 管整个壳层，出问题影响最大。它的 §4 有六条，外加一句方法：

> `min-h-0`、`min-w-0`、`minmax(0,1fr)`、`overflow` 要**沿完整父子链核对**；只给最内层 `overflow-auto` 不算实现。
> 仍须检查主区和详情的 `scrollWidth/clientWidth`。

**父子链逐层看了**：

| 层 | 类 | 作用 |
| --- | --- | --- |
| 根壳 `App.vue:11` | `fixed inset-0 grid grid-rows-[minmax(0,1fr)_auto] overflow-hidden` | 钉在视口内，`minmax(0,1fr)` 而非 `1fr`——正是 §4 点名的写法 |

### 16.16 `03 §5`/§6：路由与焦点，四处通过，外加一次扫描器翻车

**§5 不把敏感内容放 URL（通过）**。全项目只有两个 `route.query` 读取点：`?plugin=<id>`（插件详情直达）和 `?category=<名>`（设置分类定位）。都不是敏感内容。**邀请、路径、诊断内容一个都不在 URL 里**——它们都在对应的流程组件中。

**§5 表单草稿（通过）**。安装表单用 `installPath` ref 加 `v-show`，切语言不卸载组件，草稿天然保住。移除弹层的 `removeData` 虽是页级 ref，但 `askRemove()` 每次打开都重置为 false，**换目标时不会串**。

**§6 不嵌套按钮（通过）**。这一条我先写了个错的正则：`<AButton[\s\S]{0,600}?</AButton>` 配 `<AButton|<button`，结果**几乎所有文件都"命中"**。人工核对 `ErrorNotice.vue` 才看清——那里是两个并列的 `AButton`（`v-if` / `v-else-if`），非贪婪匹配跨过了第一个的结束标签。改成逐行深度追踪（遇到开标签 +1、闭标签 −1，深度大于 0 时再遇到开标签才算嵌套），结果是**零嵌套**。

**这次翻车值得记下来**：一个报出 80 多个问题的扫描器，比没扫描更容易误导——它会让人以为发现了大问题，实际是工具坏了。**先验证工具，再相信结果。**

**§6 行内动作冒泡（不适用）**。没有 `AList.Item` 带 `@click`，也就是没有整行可点的列表，所以不需要 `@click.stop`。插件行的「权限与管理」是独立可聚焦的按钮，符合 §89 后半句。

**§6 Tooltip 不夺焦点（通过）**。全项目没有用 `ATooltip` 组件，只用原生 `title` 属性——原生 tooltip 不参与焦点。

### 16.17 `06 §5` 配对流程：四条都成立

`06` 之前只在 `§7 性能` 里被顺带提过，整章是第一次读。§5 那张八阶段表里可以代码核对的有四条：

**任务存在与否不看 Modal 开关（通过）**。这是 §88 的原话，也是最容易走样的地方：

```ts
const currentTask = computed(() => pairing.snapshot && (pairing.active || pairing.snapshot.requestId !== dismissedRequest.value) ? pairing.snapshot : null)
```

判据是 `pairing.snapshot`、`pairing.active`、`dismissedRequest`——**都是 store 与任务本身的状态**。`props.visible` 只出现在四处的轮询条件里（`!disposed && props.visible !== false`），管的是"要不要继续读"，不决定"任务还在不在"。这正是该有的分工：关掉视图不停任务。

**关闭流程后仍有入口（通过）**。`DevicesPage:19` 的配对按钮文案随 `pairing.active` 切换成 `pairingResume`（继续配对），这就是 §86 要的紧凑入口。

**两种取消的文案分得开（通过）**：

| 场景 | 动作 | 取消 |
| --- | --- | --- |
| 结束进行中的流程 | `Cancel pairing` / 取消配对过程 | — |
| 移除已建立的配对 | `Forget` / 遗忘 | `保留配对`（keep） |

`forgetHelp` 还说明影响：需要重新配对、对该发送者的自动接受也会移除。文案没说"取消"，说的是"遗忘"——**两个动作在字面上就不会混**。

**confirming 阶段不编造按钮（通过）**。`PairingPanel` 里**没有 `confirming` 的任何特判**，阶段名只在文案表里出现，`confirming` 的说明是 "Confirming and saving authorization"。既然没有分支，就不可能临时长出一个本地确认按钮。八个阶段的文案也齐全（listening / connecting / confirming / cancelling / paired / cancelled / timedOut / failed）。

### 16.18 `06 §1` 默认设备页：四类事实没有互相冒充

**设备页不提供业务入口（通过）**。扫 `DevicesPage` 里 send / clipboard / transfer / share / 文件 / 发送 / 剪贴板，**零命中**。这一页只做发现、配对、连接状态与信任管理。

**`paired`、`online`、`blocked` 各管各的（通过）**。`DeviceRow` 三处各用各的字段：

- `card.online ? 在线 : 离线` —— 和配对与否无关
- `v-if="!card.paired"` 才画配对按钮
- `v-if="card.paired"` 才画已配对区的「遗忘」

一个离线设备仍然显示它已配对，没有因为离线就被说成"配对失效"。

**`blocked` 只有摘要，没有虚构命令（通过）**。`blocked` 为真时只渲染一个 warning 标签。`DeviceRow` 里**没有 unblock / 解除阻止**这类按钮——设计文档明确说"不凭字段存在就新增命令"，实现也没有加。

**详情字段完整且不截断（通过）**。展开后是 `dl`：名称、`deviceId`（`break-all`，不截断）、`address`（仅 `v-if="card.address"` 时出现）、最后发现时间。

**一处值得记的正确写法**：

```vue
<time v-if="card.lastSeenMs > 0" :datetime="...">{{ formatDateTime(card.lastSeenMs) }}</time>
<span v-else>{{ messages.devices.unknownTime }}</span>
```

用的是 `> 0`，不是真值判断。`0` 在这里走"未知时间"分支，而不是渲染成 1970 年。**第 22 轮我在任务行上正好踩过这个坑**（`startedAtMs: 0` 被 `v-if` 吞掉），这里原本就写对了。

### 16.19 `06 §2` 扫描反馈：取消要等内核说停

**未扫描不放进度区（通过）**。进度区的条件是 `v-if="scanning || scanReport || scanError"`，三者都假时整块不渲染。

**扫描中按钮变「停止扫描」（通过）**。`v-if="scanState"` 是停止，`v-else` 是开始；`elapsed/total/scanId` 收在 `<details>` 里，不在列表上方摆三列技术指标。

**失败时不伪装成本次成功（通过）**。文案 `scanFailedKnown` 写得很准：

> Showing previously known devices. **This scan did not complete.**
> 当前显示此前已知的设备，**本次扫描未完成**。

不是"扫描失败"，是"这次没完成"——旧结果还在，但它不是这次的结果。

**取消要等内核确认（通过，且这段值得单独记）**。`cancelScan()` 的顺序是：

1. `await devices_scan_cancel` —— 取消请求被接受
2. 失败就 `scanError` 并**直接 return**，不改任何状态
3. `stopAccepted = generation === scanGeneration && scanId === id` —— 只记一个标记
4. `await refresh()` —— 重新读内核
5. 五个条件全成立才写 `scanReport = 'stopRequested'`，其中包含 **`!devices.scanning`**

**第 4、5 步是关键**：接受取消不等于窗口已退出，界面不凭"命令返回 ok"就宣布停止，而是等内核回报的 `devices.scanning` 变假。

**为什么值得记**：这段的正确性全在**顺序**上。以后谁把这五步合成"取消成功就清状态"，界面就会在内核还在扫描时说已经停了——而那正是 §38 点名要避免的事。`generation` 与 `scanId` 的双重比对也是防串：慢返回的旧请求不能影响新一次扫描。

`§2` 还有两处不在本仓库：扫描器本身的行为（`devices_scan_*`）与真实网络发现，属于内核。

### 16.20 `06 §3`/§4.2 两个入口：这次是找反例，没找到

前几轮的写法是"逐条核对、记录通过"。这一轮换了方向：**假设某条没实现，去找它**。挑的是最容易被改版弄丢的三条。

**页头入口仍能导出邀请（没丢）**。`§3 L50` 特意写了一句"无目标设备时导出邀请的现有能力要保留，不能因为改成列表行入口而丢失"——这句话本身就是在防一种具体的退化。`PairingPanel` 第一步的默认值是：

```ts
const step = ref<'create' | 'accept' | 'reply'>(props.selected ? 'accept' : 'create')
```

没有选中设备时默认落在 `create`（生成邀请），**页头入口的能力还在**。

**只有 listen/connect 要求目标（没强制选设备）**。`cannotStart` 的条件包含 `!props.selected`——但这只挡住 `listen` / `connect`；生成邀请不需要目标。`§3 L51` 那句"不把每一步都强制先从发现列表选择"成立。

**附近设备入口给出名称与完整 ID（没漏）**。`PairingPanel:119`：

```vue
{{ messages.devices.pairingSelected(selected.displayName, selected.deviceId) }}
```

两个都传了。`selected` 是 `devices.get(id)` 拿到的完整 `DeviceCard`，不是只带名字的简化对象。

**信任提示确实在界面上（不是只写在文档里）**。`§4.2 L65` 要求向用户说明网络发现不能验证身份，查文案：

> Only import content received directly from the intended device through a trusted channel. **Network discovery cannot verify its identity.**
> 请仅导入通过可信渠道从目标设备直接获得的内容；**网络发现无法验证设备身份**。

中英都有，且渲染在选中设备信息下方（`HelpText`）。

**这一轮找不到反例。** 三条都是我预期可能出问题的地方，都站住了。

### 16.21 `06 §6`：输入上限用的不是契约值（已修）

上一轮说"剩下的核下去预期结果一样"。这一轮去验这句话，查了 `06 §6`——**结果不一样，找到了一处真问题**。

`§95` 原文：

> 当前最大输入长度与验证错误**沿用真实契约**；不因为界面更短就静默截断凭证。

配对面板的粘贴框写的是 `:maxlength="2200"`。查内核：

```rust
pub const MAX_INVITATION_BYTES: usize = 2048;   // 整个邀请串的上限
```

而回复走另一个校验：`> MAX_INVITATION_BYTES + REPLY_PREFIX.len() + 6`，`REPLY_PREFIX` 是 `"synra-pair-reply:1:"`（18 字符），所以**回复上限是 2072**。

| 内容 | 内核上限 | 界面允许 |
| --- | --- | --- |
| 邀请 | 2048 | 2200 |
| 回复 | 2072 | 2200 |

**2200 不是任何契约值**，是挑的一个圆整数。后果具体：粘一条 2150 字符的回复，输入框照收，内核拒收，用户白跑一趟。

**改法**：`pairingInputLimit = 2048`，一个常量加注释说明为什么取小的那个（这个框两种内容都收，回复在 2048 内仍然合法）。

**测试也换了写法**：先试 `attributes('maxlength')`，拿到 `undefined`——antd 的 `Textarea` 不总是把 `maxLength` 透传到渲染节点上。改成断言 `wrapper.html()` 含 `2048`。

**顺手删了一条自己加错的反向断言**。原先还写了 `expect(html).not.toContain('2200')`，它失败了，但查下来 2200 只出现在我自己写的注释里，与规则无关——**一个因为错误原因而失败的断言，教不会任何东西**，删掉。

### 16.22 其余硬编码常量的排查：只有 2200 是真问题

上一条的问题是「界面手写一个数字，内核有对应常量」。顺着这个特征把整个界面扫了一遍，三类：

**长度上限（1 处可疑）**。`SettingsDiagnostics` 的导出日志行数 `:min="1" :max="10000"`。查内核 `channel.rs:125`：

```rust
lines: usize::try_from(args.lines).unwrap_or(usize::MAX),
```

内核不设上限，也不会拒绝——10000 是界面给的合理约束，符合 `08 §6` 的"日志受条数预算约束"。**和 2200 不同：那个会导致"界面接受、内核拒绝"，这个不会。**

**时间间隔（0 处）**。全项目扫 `setTimeout`/`setInterval` 加三位以上数字，零命中——定时器都用常量。唯一一处 `5_000` 在 `SettingsDiagnostics`，是性能页刷新节奏，与文案"每五秒刷新"一致，属于界面自己的决定。

**声明"matching the kernel's"的常量（2 处，值对）**。`transfer.ts`：

| 前端常量 | 值 | 内核 `plugin_ui.rs` | 一致 |
| --- | --- | --- | --- |
| `MAX_TRANSFER_BYTES` | `64 * 1024 * 1024` | `MAX_PLUGIN_UPLOAD_BYTES` = 同值 | ✓ |
| `CHUNK_BYTES` | `1024 * 1024` | `MAX_PLUGIN_CHUNK_BYTES` = 同值 | ✓ |

**这两个值现在是对的**，但结构上有个隐患值得记下：**两边在同一个仓库里**（前端 `src/ipc/injection/transfer.ts`，内核 `src-tauri/src/commands/plugin_ui.rs`），却各写一份，只靠注释说"matching"。改任何一边都不会有东西报错。这是设计选择不是缺陷，**今天不改**，写在这里是因为它和 2200 是同一类风险的两种形态：一个已经漂了，一个还没漂。

**排查用的一个技巧**：搜常量名比搜数字有效。先前直接搜 `64 * 1024 * 1024`，命中一堆无关的内存、存储、HTTP 响应限制；改成搜 `MAX_PLUGIN_UPLOAD` 才一步定位到内核的声明处。

### 16.23 `06 §7` 取消配对：一次调用，没有第二次清理

`§7` 有一条最容易写错的要求：

> 现有 `devices_forget` 已撤销该发送设备的自动接收偏好，**确认中应如实说明**；这是内核已有契约，**UI 不再额外执行第二次清理**。

### 16.28 `04 §6`：十四个内核错误码原来只会说「That did not work.」（已修）

### 16.30 `healthLabel` 的类型是 `string`——追到源头发现是对的

16.29 的判据是「手抄的清单会漂，同源的不会」。顺着它查了一个可疑处：`plugins.ts` 里的

```ts
healthLabel: (health: string): string => health === 'overreaching' ? ... : health === 'degraded' ? ... : health === 'faulted' ? ... : '运行正常'
```

**参数是 `string`，最后一个是兜底**。第一反应是"收紧成联合类型，内核加第五个值就会编译报错"。

**追到源头，源头就是 `string`**。`PluginHealthDto`（`crates/synra-ipc/src/dto/plugin.rs:90`）：

```rust
/// Where it sits on the escalation ladder. `snake_case`.
pub health: String,
```

内核自己把它声明成字符串，不是 `enum Health`。所以前端没有联合类型可以引用，**兜底分支是忠实的写法，不是疏漏**。

（`Health` 枚举是有的——`synra-plugin-host` 的 `Good`/`Overreaching`/`Degraded`/`Faulted`——但它在这一层被拍平成了字符串。）

### 16.32 `kernelErrors` 八个键里六个是历史残留——但不是缺陷

16.31 补了动作文案的守卫，这一轮照同一条路查第三个表：`ErrorNotice` 的查找顺序是 `kernelErrors[message] ?? errors[code] ?? unknown`，前两个表都由索引访问，都不报错。

**`errors[code]` 那条已经在 16.28/16.31 有守卫了。这一轮查 `kernelErrors[message]`。**

**先追 message key 是怎么生成的**，答案在 `synra-ipc/src/error.rs:261`：

```rust
/// The `snake_case` name of an error code, which is what its message key ends with.
///
/// Derived from serde's own serialisation so the key and the wire code cannot disagree: a hand-written table
/// would be one more place to update when a code is added.
fn code_key(code: ErrorCode) -> String {
    serde_json::to_value(code).ok().and_then(|v| v.as_str().map(str::to_owned)).unwrap_or_else(|| "unknown".to_owned())
}
```

配合 `L222` 的 `format!("error.{}", code_key(error.code))`——**message key 就是 `error.<serde 名>`，也就是 `error.not_paired`、`error.plugin_not_installed` 这种蛇形**。而且它从 serde 派生，加了新 code 自动有 key，**不存在手工表漂移**。

**这一下把 `kernelErrors` 的形状照出来了**。它的键是驼峰：`identityHistoryMissing`、`badArgument`、`bridgeFailed`、`capabilityDenied`、`commandNotFound`、`storeUnavailable`、`timeout`、`unsupported`。

| 键 | 会不会被 `code_key` 生成 | 结论 |
| --- | --- | --- |
| `timeout` | 会（单字 code 序列化后无下划线） | 有效 |
| `unsupported` | 会 | 有效 |
| `badArgument`、`bridgeFailed`、`capabilityDenied`、`commandNotFound`、`storeUnavailable` | **不会**（会生成 `bad_argument`…） | **永远匹配不上** |
| `identityHistoryMissing` | 不会，但它是 `src-tauri` 里**手写**的 `IpcError::new(code, "error.identityHistoryMissing")` | 有效，且是唯一一处不改写 code 的地方 |

**所以这六个驼峰键是死代码。** 但它们**不造成缺陷**：匹配不上就落到 `errors[code]`，而那条在 16.28 已经补到十一个可操作 code——**界面不会因此说「That did not work.」**

**为什么仍是残留而不是隐患**：`code_key` 的注释把道理讲透了——手写表是"多加一个要更新的地方"。这六个键正是那张手写表留下来的。

**这一轮没有改代码。** 删掉六个键是纯清理，风险是万一某处真的按驼峰构造了 key；收益是少一处会让人误以为还有第二条查找路径的东西。**记在这里，不动手。**

> **⚠ 16.62 推翻了这一段并删了代码**：`ErrorCode` 带 `#[serde(rename_all = "snake_case")]`，"某处按驼峰构造 key"不可能；上面表格里 `timeout`/`unsupported` 两行写"有效"，是只看了键形状、没看有没有人发（实际命中全在测试）。整张表已删除。：`Select-String -Pattern '"error\.[a-z]+[A-Z]\w*"'` 这类正则会被 `error.aB`（测试里的变量名拼出来的字符串）之类的东西污染。判断"内核写出哪些 key"不能只看匹配结果，要看它出现在**生产代码还是 `#[cfg(test)]`**——`error.capability_denied` 那三条命中全在 `mod tests` 里。

### 16.33 `NoticeHost` 用 if 链而不是查表，所以没有同类缺口

16.32 收尾了 `ErrorNotice` 的三个输入。照同一类组件找下一个：`NoticeHost` 是提示（notice）的呈现，也在按 message 找文案。

**结构不同，而且更稳。** `headline` 是一串 `if (value.message === 'notice.xxx') return ...`，最后一行是兜底：

```ts
return messages.notices.generic
```

**没有索引访问，所以不存在"表里没有就 `undefined`"那种形状。** 未知 key 落在一句通用的话上。

**那这句兜底会不会被用户看到？** 查了生产代码（排除 `#[cfg(test)]`）：

| 发出方 | notice key |
| --- | --- |
| `deeplink.rs` | `unknownLink` |
| `shell.rs` | `dropIgnored`、`installed`、`updated`、`alreadyInstalled`、`newerInstalled` |

### 16.34 同一段查找写了两遍（已合并）

16.33 判了「if 链比查表稳」，这一轮反过来把**所有查表的地方**列出来，看还有谁在查：

```
ErrorNotice.vue:12   messages.actions[action.kind]
ErrorNotice.vue:17   messages.actions[action.kind]
ErrorNotice.vue:67   messages.kernelErrors[props.message ...] ?? messages.errors[props.code ...] ?? unknown
HomePage.vue:593     messages.kernelErrors[error.message ...] ?? messages.errors[error.code ...] ?? unknown
```

前两条是动作标签（16.31 已守）。**后两条是同一段逻辑，一字不差地写在了两个文件里**，而 `HomePage` 那份的注释自己写着：

> The same lookup `ErrorNotice` does, and for the same reason

**"same lookup" 就是问题所在。** 三行 `??` 链，两个地方要保持一致：查找顺序是**决定**而不是细节（key 比 code 具体，code 比什么都没有具体）。谁哪天在 `ErrorNotice` 里加一层（比如从 `params` 取一段），`HomePage` 那份不会跟——**同一类失败在两个屏幕上得到两种解释**，比任何一种解释都糟。

**合成一个函数**，放在 `messages/errors.ts`（三张表都在那个文件里）：

```ts
export function errorSentence(code: string, message?: string | undefined): string {
  return (message === undefined ? undefined : kernelErrors[message as keyof typeof kernelErrors])
    ?? errors[code as keyof typeof errors]
    ?? errors.unknown
}
```

`ErrorNotice` 变成 `errorSentence(props.code, props.message)`，`HomePage` 变成 `errorSentence(error.code, error.message)`。

**`message` 声明为可选**，因为不是每个拒绝都带 key——`from_synra_error` 能构造就构造，构造不出时只有 code。

**门禁**：490 条测试不增不减（这是重构，行为不变）、lint 0、check 8 项。

### 16.35 十三处相同的对象构造——我差点去改，判断是不改

16.34 合并了两处逐字相同的查找。这一轮顺着"重复"继续找，找到另一类：

```ts

```

**十三处**（`HomePage` 六处、`PluginsPage` 七处），每处手工重建同一个三字段对象：

| 位置 | 处数 |
| --- | --- |

两处 `ref` 的类型声明也是同一个形状：


**我准备做这个重构，然后停下了。** 停下的理由不是"改动大"——是**这两类重复不一样**：

### 16.39 `07 §5.2`：预览没说成已验证，能力清单在正文里

### 16.40 `07 §5.3`：安装与授权真的分开了

`§5.3` 三句话，逐条对：

**「不能顺带信任发布者」（通过）**。安装后若包带着签名，界面弹出一条 `pendingPublisher` 横幅：指纹、信任、撤销、关闭。**没有任何一步自动信任**——注释（`PluginsPage:221`）写的是：

> the plugin is off, nothing is running, and the fingerprint is something a person compares at their own pace

**「不以每个步骤都弹成功对话框」（通过）**。成功是页面内的一条 `AAlert`，可关闭，不是模态框。

**成功文案本身也守着这条边界**：

> Installed. It is switched off **until you allow what it asks for**.
> 已安装，**授予所需权限后即可启用**。

它说的是"装好了，但没运行"，不是"安装成功"四个字——`§5.3` 第一句要的正是这个。

**「成功反馈提供查看插件」（没有按钮，但形式不同，判为满足）**。`completeInstall` 做完四件事：写 `note`、清空输入、**收起安装区**（`installExpanded = false`）、重新读列表、焦点回「安装插件」按钮。

**安装区一收起，新装的插件就在正下方的列表里**——结果本来就在视线内。加一个"查看插件"按钮在这个布局里没有去处（它会是"往下看"的按钮）。**和 16.39 一样：目的达到，形式不同。**

### 16.41 `07 §6` 权限管理：新增项不会默认勾上

`§6` 六句话里，三句是硬约束。这一轮把它们和代码对上。

**「新增项不能默认全选」（通过，而且是这一节最容易写错的一句）**。权限勾选组（`PluginsPage:524`）：

```vue
<ACheckboxGroup :value="selection[plugin.pluginId] ?? plugin.granted" ...>
  <ACheckbox v-for="capability in plugin.requested" :value="capability" />
```

**框里列的是 `requested`（插件声明的全部），默认值取的是 `granted`（已授予的）。** 两者之差就是"新增项"，它们不勾。上方的注释把这两个词的区分写明了：

> `requested` is what the manifest declares, so the boxes are what the **plugin** asks for rather than what it was **given**

**「错误原因与权限请求要区分」（通过）**。`isCapabilityDenied` 是精确判定：

```ts
isCapabilityDenied: (value): value is ... => isSynraErrorValue(value) && value.code === 'capability_denied'
```

不是"任何错误都当成缺权限"，只有 code 正好是那个才判。

**「先展示当前结果：已授予、已拒绝」（通过）**。两个状态各有一行（`PluginsPage:494`、`:502`），文案 `Granted` / `Refused`，不是合并成一句"部分授权"。

**「没有变化时不显示永远可点的重复授权大按钮」（通过）**。这个按钮不是常驻的：

```vue
v-if="plugin.state === 'awaiting_consent' || permissionChanged(plugin)"
```

`permissionChanged` 比的是「当前选择」与「已授予」：

```ts
return !sameDecision(selection[plugin.pluginId] ?? plugin.granted, plugin.granted)
```

没动过 → 两边相同 → 按钮不出现。

**「允许后等待真实结果更新」（通过）**。`consent` 用的是内核回的 `outcome.value`，不是点击时传进去的那份：

```ts
pluginsStore.upsert(outcome.value)
selection[outcome.value.pluginId] = [...outcome.value.granted]
```

`toggle` 的注释把这个原则写得更直白：

> Replacing the card locally as well would be a second description of the same change, and **the two would disagree the first time the kernel answered something other than what the click assumed**.

**`§6` 六条至此全部核完，无缺陷。**

### 16.42 `07 §8` 移除：先把结果取出来，再删行

`§8` 的移除段有三句，最硬的一句是：

> 移除前按对象阻止重复操作，失败仍可定位该插件；**界面不能因为先删行就吞掉残留清理错误**

**这一条踩上去很像**：`remove()` 确实先删行（`pluginsStore.forget(plugin.pluginId)`），删了之后卡片就不在列表里了，后续的错误给谁看？

**读下去才发现不会吞**。顺序是：

1. `uninstall(...)` 返回 `outcome`——**回收量 `bytesFreed`、残留 `leftovers`、`dataKept` 都在这个返回值里**
2. 删行（`forget`）
3. 从 `outcome` 取 `freed`、`leftovers`，拼成句子写进页面级 `note`
4. 重新读列表

**关键在第 3 步：残留信息来自命令返回值，不来自那张已被删掉的行。** 注释把理由写在删行那行上面：

> No event for a removal — there is no card for a plugin that no longer exists — so the store is told directly, then the list is read once. **Forgetting here rather than only reloading means the card disappears even if the read fails.**

**「显示实际回收量/残留结果」（通过）**：

```ts
const freed = formatBytes(outcome.value.bytesFreed)
const leftovers = outcome.value.leftovers ?? []
note.value = leftovers.length > 0 ? `${kept} ${messages.plugins.leftBehind(leftovers.length)}` : kept
```

有残留时多一句，没有时只说结果。`leftovers` 在协议里是可选的（空时缺席），所以"没有"是普通情况而不是异常。

**「删除数据选项每次打开都不勾选」（通过）**：`askRemove` 第一件事就是 `removeData.value = false`（`:941`）。

**「失败仍可定位该插件」（通过）**：失败时写 `removalError` 并 `return`，**没有删行**（删行在失败分支之后），所以卡片还在，错误就贴在它上面。

### 16.43 `07 §8` 审计：靠 `revision` 而不是靠"应该没返回了"

`§8` 的审计段四句，全在讲**读取的时机与竞态**：

> 进入调用记录分类**才读** `plugins_audit`，沿用 **20 条分页**与服务器顺序；**关闭详情后停止相关读取**。
> 当前对象、offset、请求序号绑定；**快速切插件时旧响应不能覆盖新对象**。

**20 条（通过）**：`AUDIT_PAGE = 20`（`actions.ts:53`），`audit(client, id, AUDIT_PAGE, offset)` 传下去；`done` 靠"这次返回来的是不是不足一页"判断（`outcome.value.length < AUDIT_PAGE`），**不靠自己数**。

**进分类才读、关了就停（通过）**。每一次读取前都检查同一组条件：

```ts
if (!alive || !active.value || !expanded.value || busy.value || ...) return
```

四处（`L49`、`L58`、`L71`、`L90`）都是这个形状。`active` 是"这个插件的管理区展开着"，`expanded` 是"调用记录这一块展开着"——**上一级关了，下一级不会自己读**。

**旧响应不能覆盖新对象（通过，而且不是靠"应该不会"）**。`close()` 做三件事：

```ts
function close(): void {
  revision++
  expanded.value = false
  refreshQueued = false
}
```

`watch([pluginId, active])` 在**切插件或失活时立刻 `close()`**（`flush: 'sync'`，不等下一个 tick）。之后每个异步回来的分支都拿 `revision` 对一遍：

```ts
const relevant = alive && current === revision && expanded.value && active.value
```

**对不上就什么都不做。** 所以快速切插件时，A 的旧响应回来发现 `revision` 已经被 B 的 `close()` 加过，**连写都不写**。

**「关闭详情后停止相关读取」还有一层**：`onScopeDispose` 里 `alive = false` 再 `close()`，组件销毁后连 queued refresh 也不会启动（`finish` 里检查 `alive`）。

**一个值得记的写法**：这一整套没有依赖"请求应该已经返回了"这类时间假设，而是**用一个单调递增的版本号把每次生命周期变化标出来**。时间假设在慢网络下会失效，版本号不会。

**`§8` 的「同步」一段没有单独核**——它的两条（打开才读计划、保留失败列表不用绿色「已同步」）在早前漏测与假数据的记录里已经反复出现过（`plugin-page.mount.test.ts` 有「retains partial sync results and shows the failed device and structured reason」），这里不重复。

### 16.44 `07 §2`：`requested.length` 没被当成"要授权"

`§2` 那张表下面有两句话，都指向同一类错误——**用权限列表的形状去猜授权状态**：

> 只有真实有新决策时才显示"需要授权"；**不能把 `requested.length > 0` 当成始终需要再授权**。
> 权限是否已决、哪些变化需要再确认，**以内核的状态与权限语义为准**；不能用粗糙集合运算替代带范围的能力判定。

**第一句（通过）**。全项目 `requested.length` 只有一处：

```vue
<div v-if="plugin.requested?.length" class="stack gap-2">   <!-- PluginsPage:517 -->
```

它决定的是**要不要画权限清单这一段**，不是要不要显示"需要授权"。**真正决定授权提示的是 `plugin.state === 'awaiting_consent'`**（`:542`），那个值来自内核快照。

**第二句（通过，而且界面连能力字符串都没有解析）**。界面处理能力标识只有一处比较：

```ts
left.every(capability => right.includes(capability))   // permissionChanged 用
```

**精确字符串相等**。没有 `split(':')`、没有 `startsWith('net:fetch')`、没有任何按段推断的写法——grep 了 `capabilit.*split` 与 `capabilit.*startsWith`，前端零命中。

`injection/capabilities.ts:30` 那行注释正好说明了为什么这是对的：

> `network:fetch:<host>` grants, so the call either reaches the network the user allowed…

**能力是否需要"范围判定"由内核决定，界面把 `net:fetch:api.github.com` 当成一个不可拆的字符串。** 谁在界面上按冒号切分去猜，就会把"只允许 github"读成"允许所有网络"——这正是 `§2` 那句禁令针对的东西。

### 16.45 `07 §9`：发现区的三种空状态真的分开了

`§9` 有一句具体到能一眼照做的：

> 无匹配与列表加载失败、**没有注册表配置**是三种状态；**不要都画"暂无插件"**

**三种里前两种（通过）**。`PluginsPage` 的三段互斥：

| 条件 | 显示 |
| --- | --- |
| `searched && !busy && !error && results.length === 0` | `catalog.empty`（搜过，没匹配） |
| `!searched && !busy && !error` | `catalog.idle`（还没搜过） |
| `catalogError` | `ErrorNotice`（带原因和恢复入口） |

代码注释自己引用了 `§9`：

> The three states are separate on purpose… **never searched, searched with no match, and failed are not "no plugins"**, and only the first one can still offer the local install path.

**「加载失败」不是一句"暂无"，是一条 `ErrorNotice`**——它有 code、message 和可执行动作。

**第三种（"没有注册表配置"）查得绕了一段弯路，记下来**：

我先在 `registry_install.rs` 找到 `"no registry is configured for \`{package}\`"`，配的是 `ErrorCode::Unsupported`，一度以为界面会说成"此版本暂不支持"。**但那一段是安装路径，不是检索路径**（`§9` 管的是搜索与发现）。

回到 `catalog.rs` 才看清真正的形状：检索只有两个出口——

```rust
match client.packument(package, now_ms) {
    Ok(fetched) => Ok(...),
    Err(CatalogError::Unreachable { attempts, .. }) => Refusal::new(DeviceOffline, "no registry answered for ..."),
    Err(error) => Refusal::new(Unsupported, error.to_string()),
}
```

**`Unsupported` 这里是兜底，它的 message 是一句完整的话（不是 message key），带上了真正的失败原因。** 而 `catalog.rs` 开头的注释说明了为什么"没配置注册表"在检索这一侧不常见：

> `RegistryConfig`'s default is the public registry, and the answer depends on whether there is a network.

**所以我判为满足**：用户看到的是一句具体原因（或"没有注册表应答"+ 每个镜像的失败描述），不是"暂无插件"。**但这第三种状态是靠兜底分支承载的，没有专门文案**——记在这里，比声称"三种都分得干干净净"准确。

### 16.46 `07 §9`：回车才算数，中文输入法不会误提交

`§9` 除了空状态，还有三句关于"什么时候发请求"的：

> 发现搜索按当前命令语义提交，**防抖或 Enter 二者明确，不在每个按键无节制请求**。
> **输入法组合态不提交**；快速更换词/排序的旧结果不得盖住新结果。

**「二者明确」（通过，选的是 Enter）**。两个输入框都只有 `@press-enter`，没有 watch 输入值：

| 位置 | 绑定 |
| --- | --- |
| `PluginsPage:99` | `@press-enter="submitInstall"` |
| `PluginsPage:134` | `@press-enter="submitSearch"` |

`debounce` 在整个前端零命中——**没有"边打字边发"的路径**，所以"每个按键无节制请求"这件事结构上不可能发生。

**「输入法组合态不提交」（通过，而且是双保险）**：

```ts
function submitSearch(event: KeyboardEvent): void {
  if (!event.isComposing && event.keyCode !== 229) void search()
}
```

两个条件都查：`isComposing` 是标准属性，`keyCode === 229` 是**部分浏览器在组合态只报 229 时的兼容判断**。只写前者会在这些浏览器上漏判。

`SearchPalette:250` 也有同样的判断，注释说明了后果：

> An input method mid-composition sends its own keys; taking `/` there would break other layouts.

**「旧结果不盖新结果」在 16.43 核过**（`revision` 的做法），这里是同一个模块的另一处。

**三句都成立，`§9` 整节核完。**

### 16.47 `07 §10` 是清单，不是场面话

上一轮我写过一句「`§10` 是验收标准，不是逐条可对照的实现约束」——**那是没看就下的结论，错的**。`§10` 三行里有两行能够逐条对照代码。

**「菜单、行内开关与详情不会触发两次动作」（通过）**。先确认了它想防的是什么：同一个动作在**卡片上**和**详情里**各渲染一次，用户点一下可能发两次命令。

实测各动作的出现位置：

| 动作 | 渲染处 | 定义处 |
| --- | --- | --- |
| 开关 | `:352` | `:899` |
| 重试 | `:369` | `:1214` |
| 移除 | `:585` | `:937` |
| 检查更新 | `:570` | `:1168` |

**每个都是一处渲染 + 一处定义。** 顺便发现：**这个页面没有「更多」菜单**（`AMenuItem`/`Dropdown` 零命中），`§2` 示意图里那个 `[⋯]` 在实现里是平铺按钮——所以「菜单与详情重复」这种形态在这里不存在。

**「取消不修改权限」（通过）**：

```ts
function cancelPreview(): void {
  previewRevision++
  preview.value = undefined
}
watch([installMode, installPath, installExpanded], cancelPreview, { flush: 'sync' })
onScopeDispose(cancelPreview)
```

**取消只清两样东西**，不发任何内核命令。**而且它被挂得比"点取消"更宽**：换来源、改路径、收起安装区都会取消预览——`§5.1` 那句「旧预览不能用于新输入安装」正是靠这个 watch 实现的。**一个函数同时满足两节的约束，不是巧合**：它们是同一个风险的两种说法。

**没核的**：`§10` 的 `0/1/20/大量插件`、`390px/1024px/宽屏`、`键盘与触摸可完成同等管理路径`——这些要真实数据或真实视口，属于早就记过的边界（16.5、16.24）。

### 16.48 `07 §5.1`：来源确实没靠猜，但缺一条指向设置的链接

`§5.1` 四句话，三句有结论，一句**没有实现**。

**「不根据字符串是否有斜杠猜来源」（通过，而且类型帮忙）**：

```ts
const installMode = ref<'path' | 'registry'>('path')
```

**联合类型只有两个值**，用户通过 `ASegmented` 显式选，`install()` 全程没有解析 `from` 的形状：

```ts
if (installMode.value === 'registry') { await requestPreview(from); return }
const outcome = await installFrom(kernel, from)
```

搜 `includes('/')`、`indexOf('/')`、`startsWith('/')`、反斜杠——**前端零命中**。这条不只是"没写错"，是**写不错**：类型上就没有"猜"的位置。

**「表单源切换可保存各自草稿，旧预览不能用于新输入安装」（通过）**。`watch([installMode, installPath, installExpanded], cancelPreview, { flush: 'sync' })`（16.47 记过）——**换源即取消预览**。

**「注册表未配置时原位说明并链接设置「插件与来源」」（部分缺失）**。

- **说明有**：内核在安装路径给 `"no registry is configured for \`{package}\`"`（`registry_install.rs:70`），经 `ErrorNotice`（`PluginsPage:262`）原句显示。
- **链接没有**：搜 `registryHint`、`goToSettings`、`#/settings`——**零命中**。错误文案里没有去设置的路，用户得自己找到设置页。

**这一条与前面几节的差别值得写明**：`§5.2`/`§5.3` 那两次我判"形式不同但目的达到"；**这次目的没达到**——用户看到"没有注册表"却不知道去哪儿配。**缺的不是措辞，是那一步操作。**

**当时没有当场修**，理由写在纸上更该留：加这个入口要决定它长什么样（`ErrorNotice` 里加动作？还是在安装区单独一行？）——**这是个产品形态问题，我不该替用户定。所以问了。**

**用户选了"在错误提示里加按钮"，已实现**（`synra-app` `fa049e6`）：

```ts
if (!report) {
  if (failure) {
    error.value = isMissingRegistry(failure)
      ? { ...failure, actions: [{ kind: 'openSettings', section: 'plugins' } as const] }
      : failure
  }
  return
}
```

配上 `ErrorNotice` 里**早就存在**的映射：

```ts
case 'openSettings': return '/settings'
```

**所以这次改动只是把内核没给的那个动作补上，渲染路径一行没动。** `messages.actions.openSettings` 也早就有（`'Open settings'`），文案表同样没改。

**判断依据是内核那句话**，因为 `ErrorCode::Unsupported` 与另外几种拒绝共用，码本身分不出来：

```ts
function isMissingRegistry(failure): boolean {
  return failure.message.includes('no registry is configured')
}
```

**匹配散文是脆的，这一点写进了函数注释**：如果内核哪天给它单独的错误码，删掉字符串、改成 `switch` 那个码。

**两条测试，而且都验过能失败**：

| 测试 | 断言 | 破坏实现后 |
| --- | --- | --- |
| 拒绝文本含 `no registry is configured` | `actions` 有 `openSettings` | 红 |
| 拒绝文本是别的（同 `unsupported` 码） | `actions` 为 `undefined` | 红 |

第二条是关键：**它挡住了"看到 `unsupported` 就给设置链接"这种图省事的写法。**

### 16.49 想给那句字符串加一道守卫，没加成

16.48 里前端靠 `message.includes('no registry is configured')` 认出这种拒绝。**这是跨仓库的字面依赖**：内核改一个词，按钮就消失，而且没有任何东西会报错。

**这一轮想把这道守卫加到内核侧**——在 `registry_install.rs` 的测试里跑一遍那条分支，断言措辞。**试了三种办法，都不成立**：

1. **浏览器里看**——假内核的 `plugins_install` 没有这个失败分支，页面走不到。加一个只为了演示的分支，是给生产代码添东西换一张截图，不做。
2. **CLI 实跑**——`synra-cli plugin registry --clear` 能造出"无镜像"，但要先起内核，而且会改掉这台机器上的真实注册表配置。**为了验证一句话去动用户的配置，不值。**
3. **内核测试**——照抄旁边 `a_registry_that_answers_nothing_is_reported_as_offline` 的写法，结果编译不过：`scratch`、`Silent` 是**那条测试函数内部的**局部量，不是模块级的。

**第 3 条试下去还发现一个更重要的事**：那条相邻测试断言的是 `DeviceOffline`，说明它走的是"有镜像但都不应答"，**并不是"一个镜像都没有"**。而 `mirrors.is_empty()` 那个分支依赖 `RegistryConfig::new()` 的解析结果——**测试环境里根本没有走到它的办法**。

**所以那句措辞在内核侧不可测。** 我把加进去的测试删了，`synra-rust-core` 回到 0 处改动（`git status` 空）。

**这件事的结论要摆明**：

- 前端那两条测试（16.48）**守住了前端**：给它别的句子不会误加按钮，给它这句话会加。
- **没有任何东西守着内核那一端。** 有人把 `no registry is configured` 改成 `no registry is set`，两边的测试都还是绿的，只有用户会发现按钮没了。

**留给后来者的只有两处提示**：`isMissingRegistry` 的注释写了"如果内核哪天给它单独的错误码，删掉字符串、改成 switch"，以及本节。**这比有一个会红的测试弱，但比假装有守卫强。**

### 16.50 `07 §4` 的 busy：一个插件一把锁，不是整张表一把

`§4` 两句关于并发的话，是这一节唯一能直接照做的地方：

> busy 绑定 pluginId 与动作，**不能检查一个插件时禁用全部列表**，也不能同时发两个互斥的更新/移除请求。

**一个插件一把锁（通过）**。`usePluginOperations` 只有 27 行：

```ts
const busy = reactive(new Map<string, PluginOperation>())
async function run<T>(id, operation, command) {
  if (!alive || busy.has(id)) return undefined
  busy.set(id, operation)
  try { return alive ? await command() : undefined }
  finally { busy.delete(id) }
}
```

**键是 `pluginId`，值是动作名**，所以两句话同时成立：别的插件不受影响（键不同），同一个插件只能跑一个（`has(id)`）。

**界面上每一处判断都带着 `plugin.pluginId`**——`operations.busy` 的 `has`/`get` 在这个文件里出现 **14 次**，逐条看过，没有一处是全局标志（其中 13 处在模板的 `:disabled`/`:loading`，1 处在 `removalBusy` 这个 computed 里，语义相同）。

**两条防线，不是一条**。按钮本身带着 `:disabled="operations.busy.has(plugin.pluginId)"`，点不到；`run` 里的 `has(id)` 是第二道。**所以双击不会静默失败——第二下根本没打到 `run`。** `run` 的守卫防的是别处漏了禁用属性时的情况。

**`alive` 那一半也值得记**：页面销毁后 `alive = false`，`run` 开头直接返回，`command` 即使已经发出，结果也不会写进一个已拆掉的组件（`return alive ? outcome : undefined`）。

### 16.51 `07 §3`：`?plugin=<id>` 找不到时不空白

`§3` 有一句带着明确的反面：

> `?plugin=<id>` 通知链接直接打开此详情；**不存在则说明未找到并保留返回列表，不能空白**。

**这条链是完整的，三处都在**：

| 环节 | 位置 |
| --- | --- |
| 生成 | `SearchPalette:123` → `` `/plugins?plugin=${encodeURIComponent(plugin.pluginId)}` `` |
| 读取 | `PluginsPage:724` — `typeof route.query.plugin === 'string' ? route.query.plugin.trim() : ''` |
| 空态 | `PluginsPage:303` — `v-if="targetPluginId && !targetPlugin && !loading && !error"` |

**`§3` 说的是「通知链接」，实现在搜索面板里**——`SearchPalette:123` 的条目带着 `group: 'plugins'`，是全局查找的插件结果。**同一个 query 参数，通知和搜索共用一条路**，所以这个空态对两种来源都成立。

**空态那条 `AAlert` 说的是哪个 id 没找到**：`messages.plugins.notFound(targetPluginId)`，文案 `Plugin ${id} is no longer installed.`。而标题栏那一行（`:298`）显示的是 `targetPlugin?.title ?? targetPluginId`——**即使没找到，用户仍看得见自己点的是哪个**。

**一处措辞值得记**：`no longer installed` 隐含"它曾经装过"。从未装过的 id 走同一条路，字面上略微不准；但真实来源（通知指向刚被移除的插件、搜索结果指向已卸载的插件）绝大多数符合这个说法。

**「保留返回列表」也在**：`:299` 有一颗 `showAll` 按钮，`leaveTarget()` 把 `plugin` 从 query 里摘掉（`const { plugin: _plugin, ...query } = route.query`），再把焦点送回筛选框或安装按钮。

**三个条件都是必需的**：`!loading` 让它在读列表期间不闪「未找到」，`!error` 让真正的加载失败优先显示——**否则一次网络错误会被说成「没有这个插件」**。

**「就地展开不额外创建模态层」（通过）**：这个页面的详情是 `ACollapse`（`:418`），`ADrawer` 零命中。所以 `§3` 那句「关闭后回到原摘要位置与焦点」只约束覆盖式详情，**这里天然的满足方式就是没有覆盖层**。

### 16.52 `07 §4` 那张表：整节为菜单而写，实现没有菜单

`§4` 叫「行菜单的固定分组」，开头就是一张四行的表：详情/权限/调用记录 → 检查更新/同步 → 更新/重试 → 移除，按顺序排，最后一行前面加分隔线。

**这个页面没有菜单。** 我查过 `AMenuItem`、`Dropdown`、上下文菜单——**全部零命中**。动作是平铺在卡片上的按钮（`:373` 打开、`:367` 重试、`:570` 检查更新、`:585` 移除），管理区是一个 `ACollapse` 面板。

**所以那张表在当前的界面里无处对照。** 判断要分开写：

**能对照的那部分通过了**（16.50 记过）：表下面的两句——`busy` 绑 `pluginId`、不能因一个插件禁用整表、不能同时发两个互斥请求。

**不能对照的那部分是形态选择，不是缺陷**：

| 表里说 | 实现 | 判为 |
| --- | --- | --- |
| 1. 详情/权限/调用记录**导航到分类** | 一个「权限与管理」面板，三样都在里面 | 形式不同 |
| 4. 移除**在分隔线后** | 卡片末尾的 `danger` 按钮 | 形式不同 |

**关键是这三样内容都能到达**：面板是 `:418`–`:591`，`PluginAudit` 在 `:561`——**在面板内部**，展开就能看见，不需要跳转。

**「主操作、菜单与详情不得各写一套调用参数和授权判断」这条也成立**：因为没有菜单，每个动作只有一处渲染（16.47 数过）。

**结论：`§4` 的表格是为一套没有采用的界面写的。** 它描述的形态（`[⋯]` 菜单）在 `§2` 的示意图里出现过，实现选了平铺。**真正约束界面的是它下面那两句并发要求，而那两句通过了。**

**这里要小心一个过度推论**：我不能拿 `§2` 那句「示例**名称**只作结构展示」来给平铺背书——那句话说的是**名称不是真实数据**，不是「整个示意图不是契约」。`§4` 这张表是不是契约，文档里没有明说；**我判它不构成缺陷的理由只有一条：表里每一项能力都能到达**（详情、权限、审计在同一个面板里），而不是"文档说示意图仅供参考"。

### 16.53 `07 §1`：三条通过，一条在数据层就缺东西

上一轮我说 `§1`「看起来最难逐条对照」——**又判断早了。它五句话都能查**，而且最后一句查出一个真问题。

**一、默认已安装（通过）**：`const pluginCategory = ref<'installed' | 'discover'>('installed')`（`:1079`）。

**二、页内切分类（通过）**：`ASegmented`（`:28`），两个 `v-show` 段（`:127` 发现、`:295` 已安装）。

**三、三个输入区不同时常驻（通过）**：已安装筛选只在 `installed` 段里，注册表搜索只在 `discover` 段里，本地路径只在 `installExpanded` 时显示（`:89`）。**三个 `v-show` 的技术选择不影响这一条**——用户看不见就是没常驻。

**四、页头入口（通过）**：`publishers-toggle`（`:15`）展开页内 `#plugin-publishers`（`:35`），按钮文案带着待决数量。

**五、「待决策的信任问题仍需在对应对象上可见」——这条没做到，但缺的不是数据。**

`PluginSnapshot`（`ui.ts:225`）只有 `publisher: string`，结构体里搜 `trust` 零命中——**我一开始据此判"要改协议"，那个结论是错的**。

**发布者那一侧有状态**：`PublisherDto`（`ui.ts:315`）带着 `trust: string`（`seen` / `trusted` / `revoked`）。而**这个页面已经在做这个关联**，就在 `:1363`：

```ts
publishers.value.find(publisher => publisher.publisherId === report.publisherId)
```

**所以两边数据都在，按 id 对上的代码也写过——只是没用到插件卡片上。**

现在能看见的两处仍然都在页面级：装完那一刻的 `pendingPublisher` 横幅（`:224`，带指纹但**不说是哪个插件**），和入口按钮上的待决计数。

**这一条比前面所有条目都重**：`§1` 的原意是「发布者管理搬进页内入口可以，但风险不能被搬没了」。现在风险被搬到了一个需要用户自己对照的地方。

**修法也就清楚了**：卡片渲染时按 `plugin.publisher` 查一次 `publishers`，`trust === 'seen'` 就标一句。**纯前端，不用碰协议，不用碰生成流程**——这比 16.48 那次还小。

**当时只记不改**，理由不是"做不到"，而是它属于一个新的界面元素（卡片上的一行提示），**要不要加、放在哪个位置，比"两个状态分开了"这类核对更值得先问一声**。

**问过之后按选定形态实现了**（`synra-app` `f328ac1`）。三处改动：

```ts
function publisherNeedsAttention(plugin: PluginSnapshot): boolean {
  return publishers.value.some(publisher => publisher.publisherId === plugin.publisher
    && (publisher.trust === 'seen' || publisher.trust === 'revoked'))
}
```

放在 `publishers` 定义**之后**——第一版写在 `permissionChanged` 旁边，lint 报 `no-use-before-define`，挪了位置。

**条件刻意和入口计数用同一对取值**（`publishersNeedingDecision` 也是 `seen || revoked`）。**只写 `seen` 会出一件怪事**：按钮说「发布者 · 1 项待处理」，对应的卡片上却什么都没有——用户得打开面板逐个比对指纹才找得到是哪一个。**`revoked` 尤其要算进来**，因为内核在密钥被撤销后仍让插件运行，那正是不该沉默的情况。

文案 `Publisher not trusted` / `发布者未受信任`，**默认色不是警告色**——被撤销是用户做过的决定，不是插件的故障。

**三条测试，其中一条验过能失败**：

| 测试 | 断言 |
| --- | --- |
| `trust` 为 `seen` | 有标记 |
| `trust` 为 `revoked` | 有标记 |
| `trust` 为 `trusted` | 无标记 |
| 列表里没有匹配的 id | 无标记 |

**`revoked` 那条验过**：把条件改成只认 `seen`，它红了。

**`trusted` 那条验不过**——把条件改成 `trust !== 'trusted'`，三条测试全绿。**因为在这三种取值上，两种写法完全等价。** 只有出现第四种取值（新加一个中间态）时它们才会分开，而现在没有。**这是这条测试的边界，写在这里比假装它守住了什么更准确。**

**浏览器里也没看到标记，原因是数据，不是代码。** 起了 dev、打开插件页，两张卡片的状态标签旁都没有新 Tag——`fake-kernel.ts:174` 的 `plugins_publishers` 返回 `[]`，所以 `publisherNeedsAttention` 永远为 false。

**想让它出现只有一条路：往假内核里塞一条 `trust: 'seen'` 的发布者。** 那是为了截图改生产数据里的假数据，**和 16.38 拒绝的做法是同一件事**，没有做。

**所以这个标记的凭据只有单元测试**（四条，其中两条验过能失败）。**和 16.38 那个体积显示一样，属于"证明到函数层，没证明到画面"的一类。**

### 16.54 「设备库只增不减」这条旧账，已经不成立

这条在交接清单里挂了很久，两处缺口写得很具体：`devices_snapshot` 读持久化表不过 TTL、`forget_seen_devices_beyond` 生产代码零调用。

**这一轮去动手改它，发现两处都已经不是那样了。**

**缺口一：候选设备根本不读持久化表。**

```rust
let candidates: Vec<serde_json::Value> = if include_unpaired {
    host.discovery()
        .displayable(synra_core::millis_reading(now))
        …
```

而 `displayable`（`synra-core/src/discovery.rs:214`）就是过滤本身：

```rust
pub fn displayable(&self, now_ms: i64) -> impl Iterator<Item = &Candidate> {
    let ttl = self.ttl;
    self.candidates.values()
        .filter(move |candidate| candidate.is_current(now_ms, ttl) && candidate.is_displayable())
}
```

**`is_current(now_ms, ttl)` 正是当初说缺的那个判断。** 列表里那三种来源也分得清楚——配对设备读数据库（那是用户做过的决定），候选设备读内存发现表（未认证），本机单列。

**缺口二：清理有生产调用者。** `serve.rs:249` 的 `collect_loop` 调 `runtime::intents::sweep`，`sweep`（`intents.rs:173`）调 `forget_seen_devices_beyond(SEEN_DEVICE_CEILING)`，`SEEN_DEVICE_CEILING = 500`。**而且有测试盯着收敛**：`serve.rs` 写入 503 条，跑一次 `collect_loop`，断言回到 500，注释是 `"the ceiling held"`。

**为什么旧账会过时**：这条记下来的时候是对的。后来内核改过，没人回来划掉。**交接清单里最危险的不是"还没做的事"，是"已经做完但还写着没做"**——下一个人会花时间去改一个不存在的问题，就像这一轮的前几步。

**改法**：表里那一行划掉，附上这两处的位置。**留着原话但标注"已不成立"，比直接删掉有用**——它记录的是一个曾经真实存在的判断，删了以后没人知道为什么当初担心过。

### 16.56 开关拒绝时，那句话现在在自己卡片上

手工清单第 3 条（16.55 核实仍准确）里的第一条：**更新/打开/授权这些动作的错误都写在页面级 `error`**，而它渲染在 `:262`——**列表的上方**。

**触发点很具体**：卡片可以排在好几屏下面，用户点了那张卡的开关，**开关不会动**（`toggle` 失败时不写 `upsert`，`:checked` 仍来自 `plugin.enabled`），**唯一的说明在上面看不见的地方**。看起来就是"点了没反应"。

**改法**：新增一个按 pluginId 记账的 `cardErrors`。

```ts
const cardErrors = reactive<Record<string, Failure | undefined>>({})
```

`toggle` 失败时写进这张表（成功时先 `delete` 自己那一条），卡片里渲染一条 `ErrorNotice`。**按 id 记账有两个好处**：两张卡同时失败是两条独立的事实，而不是互相覆盖；重试同一张卡只清掉它自己那句。

**第一版写错了两处，都记下来**：

1. **定义放在 `toggle` 后面**，lint 报两次 `no-use-before-define`（`toggle` 里用了 `cardErrors`）。挪到 `toggle` 前面才对。
2. **加了 `@retry="retryCard(plugin)"` 和一个 `retryCard`，是死代码。**

**第 2 条值得单独说**：`ErrorNotice` 的按钮区整个包在 `v-if="actions.length > 0"` 里（`ErrorNotice.vue:8`）。**开关的拒绝不带 `actions`**，所以那里一个按钮都不会画，`retryCard` 永远没机会执行。

**这顺带说明一件事**：页面级那个 `@retry="load"`，在没有 `actions` 的错误上同样是点不到的。**这不是本轮范围，但它意味着"重试"按钮只在内核明确说"这件事可以重试"时才出现**——也许是有意的，也许不是。记在这里。

删掉 `retryCard` 和 `@retry`，只保留卡片上的说明。**用户重试的方式是再点一次开关**，这也更自然。

**两条测试，第一条验过能失败**：

| 测试 | 断言 |
| --- | --- |
| 开关被拒 | 全页只有一条 `ErrorNotice`，且它的 DOM 在 `li` 里面 |
| 第二次成功 | 卡片上的句子消失 |

把 `cardErrors[id] = failure` 改回 `error.value = failure`，第一条立刻红。

### 16.57 另外四个卡片动作，也跟进来了

### 16.63 本地那份 `ErrorCode` 是个假联合类型

16.62 删了 `kernelErrors`。照同一条路继续查 `errors.ts` 里剩下的东西，第三个导出是一个**手写的 `ErrorCode`**：

```ts
export type ErrorCode
  = | 'capability_denied' | 'device_offline' | 'invalid_argument'
    | 'not_found' | 'plugin_faulted' | 'unauthorized'
    | string            // ← 这一行让上面六个字面量变成装饰
```

**`| string` 把整个联合类型塌成 `string`。** 那六个名字看上去像约束，实际一个值都拦不住——写 `'随便什么'` 都能过。**一个自称收窄却不收窄的类型，比没有类型更糟：它告诉读的人"这里查过了"。**

**而协议侧本来就有真的那份**（`synra-js/packages/protocol/src/generated/wire.ts:99`）：22 个 code，没有 `| string`，是真正会拦的联合类型。**而且 app 里别的文件早就在用它**（`client-test-helpers.ts:11` 就 `import type { ErrorCode } from '@synra/protocol'`）。

**改法**：删掉本地定义，改成再导出。

```ts
export type { ErrorCode } from '@synra/protocol'
```

**换成真类型之后，有两件事浮出来：**

**一、协议里的 22 个 code 和本地那六个对不上。** 差的三个是 `not_found`、`plugin_faulted`、`unauthorized`——**它们在 Rust 的 `ErrorCode` 里根本不存在**（`crates/synra-protocol` 搜 `NotFound`/`PluginFaulted`/`Unauthorized` 全是 0），`wire.ts` 里也没有。**是三条写给不存在的 code 的文案，内核永远发不出来。** 按新前提直接删了（中英两侧）。

**二、两条测试拿它们当夹具。** 换掉时我没有改测试的意图，只换成一个真实存在的 code：

| 测试 | 原来 | 换成 | 为什么可以换 |
| --- | --- | --- | --- |
| `home-page`：意图失败要说清原因 | `plugin_faulted` | `plugin_not_installed` | 测的是"code 有句子就显示句子"，不测具体是哪个 code |
| `settings-page`：保存失败时语言不变 | `unauthorized` | `capability_denied` | 测的是"失败后界面停住"，同上 |

**验证类型真的生效了**：换完之后 `pnpm run check` 立刻报出这两处测试引用了不存在的属性——**旧类型不会报，因为 `| string` 让它们合法。** 这是那份假类型一直在掩盖的东西。

### 16.65 想让组件自己判断"有没有人接听"，失败了——已回滚

前面查到一个真实的形状问题：**`<ErrorNotice>` 的 `retry` 动作，七处调用点各自过滤掉**（六处内联 `filter`、一处具名 `withoutRetry`），**规则一样、写法两种**。不传 `actions` 的四处则连按钮区都不渲染。

**想法**：让 `ErrorNotice` 自己知道有没有 `@retry`，有就画按钮、没有就不画——**七处过滤全删，规则收敛到一处，还能堵住"传了 retry 却没人接"的缺口**。

**探针写出来了，结果是 `function` / `undefined`，看起来成立。**

**然后它被两次证伪。**

**第一次，探针本身是错的**：我写的探针组件**没有 `defineEmits`**。加上之后：

```
PROBE_EMITS_DECLARED=undefined
```

**`defineEmits` 声明过的 emit，Vue 会从 `attrs` 里摘走。** `attrs.onRetry` 永远是 `undefined`——**而 `ErrorNotice` 必须声明 `retry`（它要 `emit('retry')`）。**

**第二次，测试直接抓到了后果**：改完之后 `plugin-page` 的审计重试测试失败——`PluginAudit` 有 `@retry`，但按钮没画出来，`find(...)` 返回 `undefined`。

**回滚了全部改动**（组件 + 七处调用方 + 一条测试断言），`git status` 干净，门禁恢复 510 通过。

**为什么记下来而不是删掉痕迹**：

- **"七处重复"这件事是真的**，只是这个消解方式不可行。**换个方式还可以做，但前提是先确认框架允许。**
- **探针骗了我一整轮。** 它比被验证的东西少了一个关键属性（`defineEmits`），**于是验证了一个不存在的组件形态**。
- 上一轮我刚记下"一条测试可以通过而什么都没守住"。**这一轮是同一种错的另一面：一个探针可以"证明"一个方案可行，而它证明的是另一个东西。**

**下次做这类判断，探针必须由被改组件的最简真实形态构成**——至少带上它不能省的那部分（这里是 `defineEmits`）。

### 16.66 凭据面板的两个恢复出口，各自补了一条测试

16.65 回滚之后，改去看覆盖面最薄的组件：**凭据面板只有 4 条测试，而它有 4 个按钮，其中「清理密钥」是唯一不可逆的**。

| 读失败后重试 | 面板的「重新加载」必须真的重读，而不是把同一句话重画一遍 |

**第二条一开始写错了方向，值得记下来。**

### 16.75 三个状态来源都核对过了，另外两条是好的

16.74 查出插件状态表的偏差后，把**其余两个状态来源**也按同样的方法核了一遍。**结论是没有问题**，记在这里，免得下一个人再查一遍。

**意图（intent）状态：十对十，两侧完全一致。**

界面拿的是 `synra-core/src/intent/types.rs` 的 `name()`，**十个返回值**（`matching` / `choosing` / `confirming` / `dispatching` / `succeeded` / `failed` / `noHandler` / `timedOut` / `refused` / `cancelled`），**和 `home.received.states` 的十个键一一对应，中英文也一致**。

**这里有一处容易误判的地方**：同一个文件里还有 `as_str()`，返回的是 `no-handler` 和 `timed-out`（**带连字符**）。**看起来像命名不一致，其实是设计好的两套**——源码写明了理由：`as_str` 是存储和指标用的标签，`name` 是控制协议和界面用的名字，**改前者会重命名窗口已经认识的每个状态**。

- 复选框列表渲染的是 `plugin.requested`，**勾选状态来自 `granted`**——**新请求的权限默认不勾选**，这是安全的那一边；

- `operations.run` 用 `finally` 释放忙碌标记，`kernel.call` 内部把异常转成返回值，**所以 `command()` 不会抛**，不需要外面再包一层 try/catch。

### 16.86 `SettingsRow` 一个测试也没有，而它撑着每个设置字段

往下扫「没有任何测试的组件」名单时，`SettingsRow.vue` 在里面。**它只有 20 行，但每个设置项都从它过一遍**，而且两条规则坏了都看不出来：

**第一，标签是不是真的指向输入框。** 有 `forId` 时渲染 `<label for>`，没有时渲染 `<span>`。**反过来的话会留下一个 `for="undefined"` 的 label** —— 点了没反应，读屏软件还会播报一个不存在的控件。

**第二，反馈是不是另起一行。** 错误和保存结果走 `feedback` 插槽，**必须 `sm:col-span-2`**，否则那句话会挤在右边那列窄地方，压在按钮底下。

**先查了数据**：`SettingsPage.vue` 有 4 个 `for-id`，**逐个核对都指向真实控件**（`AInput` / `ASelect` / `AInputNumber`）——**数据本身没问题，缺的是让这条规则有人看着。**

**新建 `SettingsRow.mount.test.ts`，7 条**：`for` 指向、无 id 时不渲染 label、描述出现/不出现、触摸区那一对、feedback 跨列、无插槽时不渲染空行。

### 两次变异

| 变异 | 结果 |
| --- | --- |
| `:for="forId"` → `:for="undefined"` | **`expected undefined to be 'device-name'`** |
| 去掉 `sm:col-span-2` | **`expected 'min-w-0' to contain 'sm:col-span-2'`** |

**第一次我试的是删 `v-if`，得到 `no tests`** —— 又是变异把模板弄坏了、整个文件编译失败。**这已经是第三次遇到，固定做法改成：挑不破坏模板结构的变异。**

### 写测试时踩的一个坑

断言 `html()` 里有 `[&_.ant-btn]:min-h-11` **一直红**。原因是 **`html()` 序列化时把 `[` `]` 转义了**，字符串里根本不是那个样子。

**改成从元素的 `classes()` 数组里取**，绕过序列化。

**门禁**：583 测试（+7）、lint 0、check 8 项。

### 16.87 设备名冲突时只能覆盖，没有「载入当前值」

设置页里可能冲突的字段有三个：注册表地址、审计保留天数、**本机设备名**。

**提示语是同一句**，写的也是同一个承诺：

> 当前值已在其他位置更改。**可载入当前值，或明确用此草稿覆盖。**

**但只有前两个兑现了。** `registryConflict`（`SettingsPage.vue:142`）和 `retentionConflict`（`:164`）冲突时按钮变成「载入当前值」；**`nameConflict`（`:55`）只把保存按钮改成「覆盖当前值」，没有第二个按钮。**

**后果很具体**：另一个窗口改了设备名，这边正在编辑——**用户要么覆盖掉对方写的，要么取消退出、丢了自己的草稿。没有「保留对方的，重来」这条路。**

### 改法

冲突时多一个按钮，点它调 `resetName()`——**那个函数本来就在**（`useSettingsDraft` 的 `reset`），只是没人调。

```vue
<AButton v-if="nameConflict" :disabled="busy.name" @click="resetName">
  {{ messages.settings.edit.loadCurrent }}
</AButton>
```

**文案 `loadCurrent` 也早就有**，中文是「载入当前值」。

### 测试

一条：改名 → 另一个窗口改 identity → 断言出现「载入当前值」→ 点击 → 输入框变成对方的值。

**验过能失败**：把 `v-if="nameConflict"` 改成 `v-if="false"`，得到 **`no way to take the other value`**。

**类型上一次反弹**：`applySnapshot({..., scanning: undefined })` 在 `exactOptionalPropertyTypes` 下不合法，**去掉那个字段就好**——其他测试的调用本来都不写它。

**门禁**：584 测试、lint 0、check 8 项。

### 16.88 删除确认框里多了一个「重试」

这一轮的起点是往回翻文档：**L2001 早就写过「在『确定要移除这台设备吗』的对话框里重试没有意义」，并注明「这一点插件页没有做」。**

**一直没做。** `PluginsPage.vue` 那处是：

```vue
<ErrorNotice v-if="removalError" :code="removalError.code" :actions="removalError.actions" @retry="remove" />
```

**`actions` 原样传进去，所以 `Retry` 照常渲染。**

### 为什么这是重复而不是帮助

**这个对话框底部本来就有两个按钮：取消、移除。** 卸载失败后**再按一次「移除」就是重试** —— 同一个命令，两个名字。

**页面另两处（L59 / L72）已经用 `withoutRet` 做了同样的过滤**，只有这个模态框漏了。

**改法**：和其它两处一样，`actions?.filter(action => action.kind !== 'retry')`。**`@retry="remove"` 保留** —— 万一还有别的动作类型（比如去设置），键盘触发重试仍然走得到。

### 测试

**这次不用新写测试**：`plugin-page.mount.test.ts` 里已经有一条测删除失败留在对话框内的（`keeps failures inside its decision`），**它构造的失败响应恰好就是 `actions: [{ kind: 'retry' }]`**，但只断言了 `code`。

**补一句**：把断言限定在模态框内找按钮文字，确认不含「重试」。

**验过能失败**，而且输出很直白：

```
expected [ '', 'Try again', 'Cancel', 'Remove' ] to not include 'Try again'
```

**两个「重试」并排的那一行，被打印出来了。**

**门禁**：584 测试、lint 0、check 8 项。

### 16.89 `ViewLogs` 查清了：是协议预留，不是缺陷 —— 也不该删

**上一轮我把它当冗余删了，是误判。这一轮接着查，结论是另一个方向：也不该"修"，因为界面里没有能接住它的东西。**

三件事一起核了：

| 查什么 | 结果 |
| --- | --- |
| 内核会不会发 `ViewLogs` | **不会。** `synra-protocol` 里只有定义和 serde 测试，没有任何构造点 |
| 界面上有没有日志视图 | **没有。** 四个路由（`/`、`/devices`、`/plugins`、`/settings`）都不是；设置里的诊断面板只有指标和探针 |
| 内核有没有读日志的命令 | **没有。** 搜不到任何 `logs_*` 读接口 |

**三项一致：这是一条声明了、但两端都还没建的能力。**

### 那它为什么留着

`messages-errors.test.ts` 的注释写得很清楚：

> 这些是 `synra_protocol::SuggestedAction` 的六个变体。该枚举是 `#[non_exhaustive]`，**所以这份清单写在文件里、而不是从代码派生：它是提醒，不是断言。**

**文案表跟着协议走，不是跟着"谁在用"走。** 协议里有六个，文案就得有六个——**少一个，测试就红。**

**而我上一轮只查了前端"有没有人引用"，没有查协议"有没有声明"。** 这两件事查的是不同的东西。

### 它现在会长什么样

**内核不发它，所以渲染不到。** 万一将来发了，`ErrorNotice` 的 `to()` 不认识它，会落到 `v-else` 的纯文本分支——**显示"查看日志"三个字，但不带链接，因为确实没有页面可去。**

**这个降级是正确的**：`L6` 的注释说，界面接不住的动作要"以方向而不是一个点了没反应的按钮"出现。

### 结论

**不改代码。** 这条记在这里，是为了下次有人（包括我）再看到"定义没人用"时，**先问一句：是代码没写，还是协议在等代码？**

**门禁**：无改动，工作区干净。

## 18. 不作为首批前提的增强

**这一节原来把四件事并列写成一句「都按实际收益决定」，但四件的状态各不相同**（16.61 核实）：

| 项 | 状态 |
| --- | --- |
| 宽屏并排详情 | **用户已决定不做**（第 11 节，`L139`、`L147`） |
| 全局查找 | **已完成**（第 15 节） |
| 可调面板宽度 | 未做，未决定 |
| 虚拟化 | 未做，未决定 |

**同一句话里混着「已决定不做」「已完成」「未决定」，读的人无法分辨哪件还要做。** 下面按状态分开写。

**已经定了的**：宽屏只放宽宽度上限，不新增并排详情；全局查找已经实现（入口在侧栏品牌行，`/` 打开，读 store 不新增命令）。

**还没决定的两项，各自的问题**（不是"要不要做"，是"值不值得"）：

- **可调面板宽度**：现在侧栏有固定断点（`md` 折叠成图标栏，`lg` 展开）。可调意味着多一份用户可改的状态要存、要迁移、要在窄屏下处理冲突。**没有用户抱怨过侧栏宽度之前，这是给不存在的问题写代码。**
- **虚拟化**：审计 20 条一页、注册表搜索走服务器分页、日志按点击读取。**目前没有任何一个列表能长到需要它**（设备列表 16.54 已确认有 500 上限）。

**持久完成历史仍需独立查询、终态与关联契约**，当前的示例"已完成"不代表该能力已经实现。
