# 13 界面重构方案

> 2026-11-03 · 方案已用于本轮实现。原审查基线为 `synra-app@2607c33`、`synra-js@34bac6b`。
> 当前实现为 `synra-app@1228d74`、`synra-js@0eeb959`。本文保留审查与设计依据；交付、截图及尚未验证的真机范围见 [实施记录](../history/2026-11-03-ui-refactor.md)。

## 1 重构方向

Synra 需要重新组织操作与信息的关系。当前界面已经有分类、折叠、统一颜色和基本状态处理，但用户仍要在大量展开区、技术字段和并列按钮之间判断下一步。继续逐项修改圆角、收起说明、补测试，无法解决这种整体使用成本。

重构以三个结果为主：默认页面便于浏览；管理某个对象时有稳定的详情位置；安装、授权、配对等流程让用户清楚知道对象、影响、下一步和结果。

保留 Vue 3、Ant Design Vue、UnoCSS、`@synra/theme` 和首页、设备、插件、设置四个入口。沿用品牌紫作为强调色，收敛工作面上的渐变、告警底色和重复容器。插件业务仍由独立插件页面提供，宿主管理页负责安装、权限、更新和设备关系。

建议先制作**插件列表与详情、权限决策、配对双方**四个目标画面，在同一套视觉尺度下评审，再分批替换现有界面。

## 2 现状与证据

### 2.1 本轮检查范围

本轮在本地 Vite 浏览器预览中检查四个主页面、插件管理展开区、安装区、发现搜索和全局搜索，并对照 Folo 公开 Web 应用的导航与设置、已有列表与更多菜单截图。Synra 的实时检查视口为 **1280×720 CSS 像素**。

浏览器预览使用 FakeKernel，注册表搜索固定返回空数组，不能用于判断真实搜索结果质量；配对双方弹窗依据生产组件、状态与上一轮回归结果核对，没有将预览当作真实配对。手机布局参考已有 2026-10-30 截图，390×844 与鸿蒙卓易通实机检查列入后续验收。

## 3 对照 Folo 应采用的方式

Folo 的参考价值在于稳定的对象上下文和清楚的操作层级。它的阅读业务、三栏布局、登录流程与配色不直接移植到 Synra。

| Folo 中可观察的组织方式 | Synra 当前的差距 | 本方案采用的方式 |
| --- | --- | --- |
| 列表负责辨认和选择，详情承担完整内容 | 插件详情展开后成为列表的一部分，浏览位置不断移动 | 列表与单对象详情分开，关闭详情恢复原列表上下文 |
| 对象工具栏保留常用操作，低频动作进入更多菜单 | 多个管理按钮与技术内容在展开区并列 | 打开、需处理状态常显；同步、审计、移除等有固定去向 |
| 设置通过分类、对齐与较轻的说明建立秩序 | Synra 已有分类，但容器、重复标题和间距仍偏重 | 保留分类设置页，调整行与分组，不改造成 Folo 同款设置弹窗 |
| 输入、按钮、菜单共享一致的视觉语言 | 原生搜索 input 与 Ant Design 控件混用；小号按钮被外层样式覆盖 | 输入与交互控件统一使用现有组件体系，尺寸规则集中处理 |
| 控件围绕当前任务出现 | 安装、发布者、发现、权限可以同时展开 | 安装作为流程，发布者作为低频管理，详情一次只管理一个插件 |

参考依据为 [Folo 公开应用](https://app.folo.is/)、[官方仓库](https://github.com/RSSNext/Folo) 与 [01 的固定版本研究](./01-folo-reference.md)。本轮公开应用可观察导航和设置；列表详情与更多菜单对照使用[已保存截图](./evidence/README.md)，不把匿名页面当作完整功能测试。

## 4 视觉与控件尺度

### 4.1 建议尺度

下表是首版样稿的起点，使用现有 token 的等价值；长文本、系统字号与缩放可以使内容增高。

| 对象 | 桌面精细指针 | 手机与粗指针 | 说明 |
| --- | --- | --- | --- |
| 页面标题 | 20px，中等字重 | 20px | 当前 `text-xl` 实际映射为 26px，不继续把最大字号用于所有页头 |
| 对象名称与正文 | 14px；重要名称适度加重 | 14–16px | 根字号保持系统默认，不整体缩放页面 |
| 次级说明 | 12–13px | 13px 起 | 减少重复信息，必要影响和错误保持正文可读性 |
| 标准按钮与表单控件 | 高 32px | 命中范围至少 44×44px | 常用确认、页头操作采用同一标准 |
| 行内次要按钮与图标按钮 | 视觉及命中高度 28px | 命中范围至少 44×44px | 小图标可以位于较大的可点击容器内，命中范围不互相覆盖 |
| 正常对象摘要 | 通常 56–72px | 随内容增长 | 不固定截掉错误、长名称或双语内容 |
| 权限决策行 | 用途、范围、状态形成完整行 | 整行可点，至少 44px 高 | 不只扩大 16px 的勾选图标 |
| 短确认对话框 | 宽约 400–440px | 两侧留安全边距 | 配对、忘记等短流程不使用大型表单布局 |
| 插件安装与权限流程 | 宽约 560–640px | 单列或全宽流程 | 标题、正文滚动区、页脚清楚分离 |

触控范围根据输入能力处理，不能继续只靠 `md:` 判断。触摸笔记本也需要可点的控件。WCAG 2.2 AA 的 [2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) 使用 24×24 CSS 像素及例外条件；[2.5.5](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) 的 44×44 是增强级要求。本项目继续采用 44×44 的触控目标，不将它解释为所有桌面按钮必须画成 44px 高。

### 4.2 应集中修正的样式规则

- 在 `@synra/theme` 定义和映射控件密度，在宿主统一选择使用方式，逐步移除页面对所有后代 `.ant-btn` 的高度覆盖。
- 确认按钮、行内动作、更多入口分别定级。同一上下文最多一个主色动作；不能把“拉黑、拒绝、同意”做成三个同等强调的按钮。
- 关闭 Ant Design 双汉字按钮自动插空格的行为，统一呈现“配对、安装、搜索”，保留真实文本中的空格。
- 输入框、选择器、按钮、开关共用字体与焦点风格；全局搜索改用现有输入控件，避免再叠一层浏览器默认边框。
- 分组优先用标题、间距与轻分隔。保留表达对象或模态层的容器，减少卡片里再套卡片和大块重复告警。
- 工作面保持稳定，品牌紫主要表达选中、焦点和主动作。正常在线／运行状态不使用大面积成功底色。
- 保留可见焦点、对比度、reduced motion 和原有语言支持；不能用更小更淡的文字替代信息重组。

## 5 设备与配对

### 5.1 设备页

默认视图用清楚的分组和紧凑行显示名称、平台、连接情况。附近设备常显“配对”，行名进入详情，更多入口容纳低频动作；“详情”不再与主动作占据两个等宽的大按钮位置。完整 ID、地址、发现时间在详情可读、可复制。

```text
设备                                            扫描

已配对
设备图标  工作电脑       Windows · 在线                ⋯

附近设备
设备图标  安卓           Android                配对   ⋯

已阻止设备按需展开
```

“忘记”与“拉黑”分开说明。忘记移除本机关系与相应偏好；拉黑持续拒绝对方。当前实现可通过“忘记”删除 blocked 记录，首批保留这条真实路径，不只改成一个没有相应契约的“解除拉黑”按钮。

### 5.2 配对弹窗

弹窗以设备名称、六位码和当前状态为核心。六位码使用等宽数字，不加引号，不做输入框或六个验证码格子；它是核对信息，无需用户输入。

| 状态 | 内容 | 操作 |
| --- | --- | --- |
| A 等待 | 与安卓配对、配对码、等待对方确认 | 取消配对 |
| B 待决定 | 工作电脑请求配对、同一码、核对提示 | 主动作“同意”，次动作“拒绝”，较弱的危险动作“拉黑” |
| 正在提交 | 保留对象和码，阻止重复操作 | 对应提交状态，不抢先显示成功 |
| 成功 | 已与目标配对，设备列表同步变化 | 完成 |
| 拒绝、取消、超时、联系不上 | 目标和准确结果 | 关闭；可重试时给重试入口 |

```text
A                                    B
与安卓配对                            工作电脑请求配对

          123456                                123456

等待对方确认                          请核对另一台设备上的配对码

                    取消配对           拉黑        拒绝   同意
```

沿用当前关闭语义：A 的关闭／Escape 等于撤回，B 等于拒绝；关闭控件的可访问名称明确表达这一动作。未决状态不因失焦或点击遮罩而消失，也不提供一个含义不明的“关闭但继续等”按钮。

超时、拒绝与连接失败必须来自明确结果。若现有实现只把状态清回 idle，需单独补足状态通知，不能由新界面根据弹窗消失或计时器自行猜测原因。

全局接收请求与安装、权限等弹层需要统一协调。已有模态流程时先保留草稿并给可操作的全局待处理提示，用户进入配对后暂存原流程；不得在授权框上再叠一个配对模态框。后端仍只有当前那份请求，UI 不伪造多份配对队列。

## 6 插件列表与详情

### 6.1 默认页面

保留“已安装／发现”。页头的主要安装入口改为具名的“从本地安装”，发布者管理进入页头更多菜单；有待处理决定时保留可见摘要。默认已安装列表只显示名称、短描述、一个主要状态、可用的打开入口、启用开关和更多。

```text
插件                                  从本地安装   ⋯
已安装    发现                 筛选已安装插件

GitHub links    打开共享的仓库链接      运行中    开关   ⋯
Touchpad        远程触控              已停用    开关   ⋯
Shortcuts       需要检查权限          检查权限   开关   ⋯
```

示意中的插件仅表达管理结构，不新增宿主业务。无 UI 插件没有“打开”。待授权对象有直达权限的入口，故障对象有就近恢复入口，普通更新只显示轻量提示；安全相关变化在决策处完整呈现。

### 6.2 详情承载方式

选择一个插件后进入稳定详情，建议分为“概览／权限／调用记录”。概览包括版本、发布者、实际运行状态、更新与故障摘要；技术字段和配额按需阅读。

首批采用现有组件库的单个 Drawer／全宽详情，不建设固定三栏。宽屏确有连续对照需要时，再评估列表与详情并排；1024px 下必须完整可用。详情关闭后保留分类、筛选、滚动与焦点，通知链接继续按完整插件 ID 定位。

更多菜单按“查看与管理／更新与同步／移除”分组；审计清除、移除与保留数据的选择仍有明确确认。菜单、详情和快捷操作共用现有动作执行规则，不复制第二份权限判断。

## 7 权限选择

权限页默认呈现可理解的决策项。用途、范围、当前决定与这次变化放在同一行，删除“已授予标签清单”与“所需权限复选框”的重复布局。已授权的正常查看先显示结果，进入编辑后才出现可修改表单。

```text
Shortcuts 的权限
新增 1 项权限

已允许   打开本机链接
         使用系统默认程序打开链接             查看标识

未决定   访问指定站点                         新增
         api.github.com                允许此项 □

                              取消修改   保存权限
```

示意中的人类可读名称是展示层说明，真实能力标识与范围必须完整可查，不能将某个指定域名的权限概括成不带范围的“联网”。未知能力保留原标识和明确的未知说明，不能自行猜测用途。

决策语义以现有内核为准：`consent::decide` 支持部分授权，未选项会记为拒绝；界面不能把全部权限都标成必需，或诱导用户全选才能继续。已有允许项准确回填，新增项默认不允许；未改动时不显示无意义的保存动作。

首次授权用“允许所选权限”表达决定，修改既有决定用“保存权限”。若插件已经启用，保存决定可能立即使其开始运行，当前影响需要在确认处说明；不要在返回真实状态前显示“已运行”。拒绝全部、保留停用、部分授权和运行失败分别呈现。

更新流程优先展示新增权限及其范围，再提供完整清单。关闭／取消不提交修改，外部事件不覆盖未保存草稿；换插件和换版本时不得提交上一份决定。

## 8 安装与搜索

### 8.1 本地安装

“从本地安装”打开独立流程，首先选择插件包或插件目录；选择器是主要入口，手动路径放在高级展开项。不要让普通用户先填路径，再从三个同等按钮中判断如何安装。

目录和插件包分别命名，选中后显示文件名、来源和可读取的信息。安装中保持进度与对象，失败保留选择和原因。当前本地安装没有独立的完整预览接口，首批按真实能力完成校验与安装，再进入权限处理，不画未经读取或验证的预览结果。

### 8.2 发现与注册表安装

发现页只有一套远端搜索。名称或精确插件 ID 都从同一输入进入，Enter 或搜索按钮提交；已安装筛选继续是本地即时筛选。输入用途通过标签和上下文区分，不只靠不同 placeholder。

排序是次要控件，窄屏换到下一行或筛选入口。无来源配置、尚未搜索、搜索中、无匹配、请求失败、有结果分别显示；没有浏览接口时，不虚构热门推荐、分类或市场首页。

结果用名称、描述、版本、发布者和安装状态帮助判断，点击名称进入详情，按钮使用“查看详情／安装／已安装”等用户能理解的动作；“预览”只是实现步骤，不作为用户理解流程的前提。分页保留已有结果，失败就近重试。

```text
发现插件
搜索名称或插件 ID                         搜索
                                  排序：相关性

插件名称        一句描述           版本／发布者
                                            查看详情
```

### 8.3 安装后的下一步

安装流程明确区分：取得插件、校验实际产物、发布者决定、权限决定和实际运行状态。安装成功后在当前流程提供“查看插件／检查权限”，不再让用户滚回列表寻找新对象，也不在每个步骤重复弹成功框。

注册表预览里的发布者和能力是声明；下载后的签名校验才是真实校验。信任发布者与授予插件权限分别说明影响，不预选未来信任；现有发布者接口没有“一次性信任”决定时，不添加这类按钮。

安装可能在用户关闭视图后继续；只有现有契约支持真正取消时才显示“取消安装”。关闭的影响要明确，不能把隐藏表单当成任务已取消。

### 8.4 全局搜索

全局搜索用于导航到已安装插件、本机已知设备、设置和页面，不与发现页远端搜索混用。采用统一输入样式；空输入可给少量页面／设置快捷入口，不引入需要新持久化的最近搜索系统。结果按对象类型分组，说明它将打开的对象和位置。

桌面支持 Ctrl/Cmd-K，保留当前 `/` 快捷键和输入法保护。键盘选中、鼠标悬停、焦点三种状态可区分，Escape 后返回触发位置；触摸端有可见退出入口，搜索不依赖点击遮罩才能关闭。

## 9 首页 设置与公共反馈

首页保留简洁连接摘要、待处理事项、进行中任务与真实记录。空的传输、文件分组使用短反馈或合并的空状态，避免每个空分组占一张大面板。任务与收到文件保持各自含义，不新增文件发送、打开等插件业务入口。

设置保留现有五类结构和 `SettingsRow`，去掉重复分组标题，统一标签、值、说明与控制项对齐。错误和保存状态属于对应设置项，诊断继续按需读取；浏览器预览的“不支持”不能被写成 Native 功能坏了。

四页共用以下反馈规则：正在操作时只锁定相关对象；成功更新实际状态并给短反馈；失败就近保留原因与恢复入口；待决策和失败不自动消失。长弹窗只滚正文，底部动作可达，软键盘不得遮住主要操作。

右下角线缆监视保留现有入口、设置与终端功能。首版样稿比较较低饱和度和较小视觉尺寸，命中范围仍合格；未读标记不替代产品错误提示，不通过改默认配置来回避视觉问题。

### 10.2 推荐实施顺序

| 批次 | 交付内容 | 完成条件 |
| --- | --- | --- |
| A 目标画面与规则校正 | 插件默认页及详情、权限决策、A/B 配对四个画面；固定正常、待授权、搜索结果与失败样例；统一尺度；修订互相冲突的条目 | 用真实长短名称、正常与待处理状态评审，明确主动作和关闭行为后再批量改页 |
| B 公共密度与设备配对 | 主题密度、原生输入残留、按钮插空格、设备行和配对弹窗 | 桌面小号动作不被撑大；触控仍可点；双端确认与取消语义保持正确 |
| C 插件列表与权限 | 稳定列表、单对象详情、权限用途与范围、更新权限差异、固定管理动作去向 | 查看一个插件不再撑开整个列表；部分授权、草稿和异常恢复正确 |
| D 安装与发现搜索 | 本地安装流程、单一注册表搜索、对象详情到安装、安装后下一步 | 不重复输入 ID；不在三个安装按钮间猜测；空、错、等待和成功各有准确反馈 |

每个批次完整交付一条用户路径，不按“改一个 class、补一个断言”连续拆成大量缺乏体验结果的小轮次。前面已稳定的配对和插件状态机作为回归边界，不能在视觉重构中顺便改变。

## 11 验收方式

### 11.1 必须走通的路径

| 场景 | 通过条件 |
| --- | --- |
| 浏览已安装插件 | 在 1280×720、默认缩放、至少五项正常样例下，首屏能浏览多个完整摘要；没有默认展开的权限表单或成片告警 |
| 管理一个插件 | 可直达详情、权限和调用记录；返回时原筛选、列表位置和焦点保留；其他对象仍可辨认 |
| 修改权限 | 用途、范围和当前决定可读；新增不默认允许；部分授权按内核执行；取消不写入；失败不丢草稿 |
| 本地和注册表安装 | 来源明确；选择、校验、安装、权限与结果可理解；失败保留对象；实际没有取消能力时不显示假取消 |
| 配对 | PC→Android 与 Android→PC 两向同码；A 等待且可取消；B 可同意、拒绝、拉黑；终态准确；旧构建问题与新布局分开核对 |
| 搜索 | 三种搜索范围不混淆；Enter 与中文输入法行为正确；旧响应不覆盖新输入；错误不冒充无结果 |
| 多流程冲突 | 安装／权限未决时收到配对请求，仍有可达的处理入口，草稿保留，没有两层模态框争抢焦点 |
| 异常与空状态 | 0／1／多项、同名、长 ID、长路径、长权限、运行故障、更新新增权限都能明确操作 |

### 11.2 视觉和环境检查

同一批次保存同内容、同视口的前后截图。至少覆盖插件默认、插件详情、权限决策、本地安装、发现搜索、配对 A/B 和设置；检查正常、错误与操作中状态。普通桌面按钮密度、手机命中区域和 200% 缩放分别检查，不能用一个尺寸兼任三种证明。

浏览器检查至少包括 390×844、768、1024、1280、1904 宽，中英文、键盘和输入法；最终在 Windows WebView2 与鸿蒙卓易通里的 Android WebView 验证系统文件选择、软键盘、模态框和双端配对。Native 验收要记录构建对应提交，安装版含旧前端资源时不判定新方案失败或通过。

模态框的焦点进入、Tab 范围、Escape 与焦点归还按 [WAI 对话框模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) 检查；配对关闭对应撤回／拒绝，其他流程按各自已定义的关闭语义执行。

纯样式以实际渲染、尺寸和操作为主，不为 class 名称另写一批镜像测试。异步竞态、部分授权、焦点恢复、关闭语义、重复提交和弹层冲突使用行为测试。前端变更执行相关测试、lint、类型／构建和 shapes；主题变更增加适配和对比度检查；仅在 Rust 或 IPC 受影响时运行相应内核检查。

**每批完成记录要回答：什么场景变得更容易，截图显示什么，哪些操作已实际走通，还有什么问题。测试数量不再作为整体体验完成的替代证明。**

## 12 首批建议

从批次 A 开始，以插件页为主要目标画面，同时给出权限决策和 A/B 配对对话框。先确定密度、详情承载方式、主次按钮和权限表达，再进入批次 B、C。安装与发现随后接入同一套结构，最后收敛首页、设置和全局反馈。

首批保留现有数据模型与内核能力，不以更换组件库、增加市场后端、重做传输或添加持久历史作为前置条件。
