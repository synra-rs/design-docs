# 06 · 设备与配对

> 🟡 页面候选方案。设备可采用面板、卡片或简洁行；下文以行说明信息与动作，不把列表当作目标。配对状态与安全要求保持不变。

## 1. 默认设备页

设备页负责发现、配对、连接状态与设备信任管理，不提供发送文字/文件、远程剪贴板等业务入口。
默认看到设备概况与可辨认的对象摘要，配对说明仅在开始配对时出现；页面头部提供“配对设备”，扫描是发现操作，可作为次级按钮。
扫码/二维码若将来加入，必须有实际协议和平台支持；本轮不把它写成已有能力或首批前置条件。

```text
设备                              [扫描] [配对设备]

已配对
  Pixel 8             Android     在线             [更多]
  Work PC             Windows     离线             [更多]

附近设备
  unknown-android      Android     未配对       [配对] [更多]
```

| 位置 | 默认字段 | 详情字段 | 操作 |
| --- | --- | --- | --- |
| 已配对行 | 名称、平台、在线/离线、阻止状态（若有） | ID、最后发现时间、已有可用信息 | 查看详情、取消配对；其他动作仅在已有支持时展示 |
| 附近设备行 | 名称、平台、未配对 | `address`（若有）、完整 ID、发现时间 | 配对、查看详情 |
| 页头 | 标题、扫描状态/动作、配对入口 | 扫描进度展开后可看时长/数量 | 扫描、扫描中取消 |

不能为了新详情给已配对设备补一个前端猜测的地址：当前 `DeviceCard.address` 主要只为未配对设备提供。
`paired` 与 `online` 是两种事实；“离线”不等于配对失效，“发现”不等于可信，“未配对”不应默认整行红色告警。
`blocked` 若为真必须有明确摘要，详情操作仍以实际契约为准，不凭字段存在就新增“解除阻止”命令。

## 2. 扫描反馈

未扫描时不放进度区；扫描中把按钮替换为“停止扫描”，用紧凑进度和已发现数量即可。
详细 elapsed/total、scanId 放折叠详情，不在默认列表上方展示三列技术指标。
扫描结束保留已有结果，短反馈说明找到多少；没有发现时说明可检查同一网络，并提供重试，不宣称网络已排障成功。
扫描失败就在列表头部给原因和重试；旧结果若仍显示，标明是已知结果，不能伪装为本次扫描成功。

## 3. 配对流程的两个入口

当前协议以可信渠道交换邀请/回复，不能简化为发现设备后自动授权。
推荐在一个 Modal/全宽流程中明确角色，避免默认把两套动作同时铺开。

| 入口 | 用户目的 | 首个可见操作 |
| --- | --- | --- |
| 页头“配对设备” | 从这台设备发起交换，尚未选择附近设备 | 生成此设备的邀请；或切换到“已有邀请/回复” |
| 附近设备“配对” | 已知道目标设备 | 显示目标名称/完整 ID，选择输入邀请还是回复 |

**无目标设备时导出邀请的现有能力要保留**，不能因为改成列表行入口而丢失。
只有接收方 listen/connect 需要目标时才要求选择，不把每一步都强制“先从发现列表选择”。

## 4. 建议分步流程

### 4.1 生成邀请的一方

1. 点击“配对设备 → 生成邀请”。说明仅一小段：将邀请通过可信渠道交给另一台设备。
2. 生成后显示只读邀请与明确复制入口；原始文本仍可手动选中，复制失败有文字提示。
3. 等待对方生成回复；需要提交回复时选择实际目标，粘贴回复，按钮标成“验证回复并连接”。
4. 连接中显示实际 `PairingSnapshot.phase` 与截止时间，提供明确取消；以 paired 结果结束，不以点击按钮视为成功。

### 4.2 接受邀请的一方

1. 从附近设备点击“配对”，或从配对入口选择“已有邀请”。
2. 显示选中设备名称/ID，粘贴其邀请；说明“网络发现不能验证身份，请通过可信渠道核对交换对象”。
3. 点击“接受邀请并生成回复”，对应现有 listen 路径。
4. 得到回复后显示只读文本/复制入口，提醒把回复交回邀请方；保持 listening/confirming 等真实状态。
5. 内核确认 paired 后才显示成功并更新已配对分组。

以上是对现有 `pairing.exportInvitation()`、`pairing.listen()`、`pairing.connect()` 的交互编排，不新增跳过验证的快捷握手。
若实际契约不能把邀请与回复自动区分，就保留显式角色选择，不能只靠字符串特征猜测协议对象。

## 5. 流程状态与退出

| 状态 | 主内容 | 允许操作 |
| --- | --- | --- |
| 未开始 | 角色、目标、必要输入 | 切角色/目标、粘贴、生成邀请 |
| listening | 回复内容、等待对方说明、截止时间 | 复制回复、明确取消 |
| connecting | 正在验证/连接的短状态 | 取消（内核允许时） |
| confirming | 等待双方完成确认 | 按实际协议呈现，不编造本地确认按钮 |
| cancelling | 正在取消，保留目标 | 防止重复取消/新发起 |
| paired | 已配对、对象名称 | 完成，返回设备列表 |
| cancelled / timedOut | 已取消/已过期与下一步 | 明确重新开始，不自动重用旧邀请 |
| failed | 错误原因和可执行建议 | 修正输入、重新读取状态/重新开始 |

关闭流程只关闭视图；若任务在继续，设备页保留紧凑“配对进行中”入口，可返回当前任务。
如果用户要结束任务，点击明确的“取消配对过程”，等待内核结束；“取消配对过程”和“取消已建立的配对”文案必须区分。
当前 `requestId/peerId/phase` 来自 store，不用 Modal 开关推导任务是否存在。

## 6. 文案、安全与长内容

完整安全提醒在真正交换邀请/回复处显示，不能仅放进 tooltip；日常设备页不重复整段协议教程。
ID/地址可在只读预览辅助辨认，**不得标成“已验证”**；同名设备仍须有完整 ID 区分。
邀请/回复不写 URL、不发日志、不存成跨会话 UI 偏好；复制是用户明确操作，不自动读取其剪贴板。
当前最大输入长度与验证错误沿用真实契约；不因为界面更短就静默截断凭证。

## 7. 取消配对

从已配对设备更多菜单末尾进入，确认框写明目标、取消后的连接影响；不把它放在默认行最显眼的位置。
取消成功等待真实状态更新；失败保留配对状态与原因。不能自动删除插件、历史、接收文件或其他设备的配置。
如果产品需要同步撤销“自动接收”等授权，应先定义契约，不能由 UI 私自顺带清理。

## 8. 验收

无设备、只有已配对、只有附近设备、混合列表、同名设备、长 ID；扫描中/结束/取消/失败；配对两种角色与无目标导出入口。
重点验证关闭后重入、换页后回到进行中任务、超时与旧回复、取消中重复点击、IPC 失败、手机软键盘和只读文本复制。
真实双设备握手与系统剪贴板需 Native 验证；纯浏览器假内核只能证明界面流程与调用参数。
