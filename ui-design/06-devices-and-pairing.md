# 06 · 设备与配对

> 🟡 页面候选方案。设备可采用面板、卡片或简洁行；下文以行说明信息与动作，不把列表当作目标。配对状态与安全要求保持不变。

## 1. 默认设备页

设备页负责发现、配对、连接状态与设备信任管理，不提供发送文字/文件、远程剪贴板等业务入口。
默认看到设备概况与可辨认的对象摘要；配对从附近的某一台设备开始，页头只留“扫描”。
扫码/二维码若将来加入，必须有实际协议和平台支持；本轮不把它写成已有能力或首批前置条件。

```text
设备                                     [扫描]

已配对
  Pixel 8             Android     在线             [更多]
  Work PC             Windows     离线             [更多]

附近设备
  unknown-android      Android     未配对       [配对] [更多]
```

| 位置 | 默认字段 | 详情字段 | 操作 |
| --- | --- | --- | --- |
| 已配对行 | 名称、平台、在线/离线、阻止状态（若有） | ID、最后发现时间、已有可用信息 | 查看详情、取消配对；其他动作仅在已有支持时展示 |
| 附近设备行 | 名称、平台、未配对 | `address`（若有）、完整 ID、发现时间 | 配对、查看详情 |
| 页头 | 标题、扫描状态/动作、配对入口 | 扫描进度展开后可看时长/数量 | 扫描、扫描中取消 |

不能为了新详情给已配对设备补一个前端猜测的地址：当前 `DeviceCard.address` 主要只为未配对设备提供。
`paired` 与 `online` 是两种事实；“离线”不等于配对失效，“发现”不等于可信，“未配对”不应默认整行红色告警。
`blocked` 若为真必须有明确摘要，详情操作仍以实际契约为准，不凭字段存在就新增“解除阻止”命令。

## 2. 扫描反馈

未扫描时不放进度区；扫描中把按钮替换为“停止扫描”，用紧凑进度和已发现数量即可。
详细 elapsed/total、scanId 放折叠详情，不在默认列表上方展示三列技术指标。
扫描结束保留已有结果，短反馈说明找到多少；没有发现时说明可检查同一网络，并提供重试，不宣称网络已排障成功。
扫描失败就在列表头部给原因和重试；旧结果若仍显示，标明是已知结果，不能伪装为本次扫描成功。
取消请求被接受不等于发现窗口已经退出；在内核确认结束前保持等待，不提前宣布停止。内核现已接入可唤醒取消、结束通知和任务归属隔离；命令级测试已通过，桌面与真实网络验收仍见 [当前进展](./11-current-progress.md)。

## 3. 配对是一个请求，不是一次交换

**配对只有一个入口：附近设备行上的“配对”。** 点下去就是向那台设备发起配对请求；
它收到后显示一个请求条，用户点“接受”即可；两边都完成，配对建立。

没有一个需要抄给对方、再抄回来的邀请码，也**没有证书需要用户搬运**。曾经有过——一段文本从 A 复制、
粘贴给 B、B 再生成一段回复抄回 A——那是协议在要求「先有对方证书才能连接」，而证书只能靠人送过去。
现在两条连接在这一步都不再要求预置：首配的连接先交换证书，再把两个 device id 推出的六位数码
显示在两边屏幕上，由人对一眼确认。**证书仍在，只是不再经过用户的手。**

**保留的只有可信性，去掉的是搬字。** 一台设备收到请求时，弹窗里必须显示发起方的完整 ID 与名称、
它所在地址，以及那六位数码——**发现只能证明“同一网络里有这样一个地址”，不能证明那是谁**；
数码一致只证明两台设备说的是同一次请求，也不证明对方是谁。用户接受时是在确认他认识这个对象，
这与手工核对邀请码要达到的是同一件事，只是不再需要他自己当传输通道。

页头不再需要“配对设备”按钮：没有选择目标时，配对无从谈起。
“扫描”仍是发现操作，保持在页头。

## 4. 流程

### 4.1 发起的一方（A）

1. 扫描，附近设备里出现目标。
2. 点该行的“配对”。**请求立刻发出**，不先弹一次本机确认 —— 本机这一步唯一要做的判断是“点的是哪一行”，
   那一行本身就是判断。多弹一次只会让每次配对多一次没有信息量的确认。
3. 面板顶部出现“等待对方确认”：目标名称、**大号等宽的六位数码**，以及“收起”。
   数码当场就算出来（由两个 device id 推出），不必等对方先回话。
4. 对方接受后，A 的行移入已配对，等待区块自行消失；对方拒绝或超时，等待区块保留到窗口结束，行回到未配对。

**A 不需要在配对过程中做任何输入。** 没有要粘贴的东西，也没有要读给谁听的东西——数码是看给对方确认的。

### 4.2 被请求的一方（B）

1. 收到请求时**弹出一个请求条**，位于设备页之上，不阻塞其余界面：
   显示发起方完整 ID 与名称、来源地址、“请求与这台设备配对”、**同样大号等宽的六位数码**，以及“接受 / 拒绝”。
2. 点“接受”→ 配对建立，请求条消失，对方出现在已配对。
3. 点“拒绝”→ 请求结束，A 那边收到“对方拒绝了配对请求”。
4. 不理会 → 到期自动失效，A 收到超时。

**请求条不自动消失、不自行默认接受。** 一个能被忽略而消失的请求，
等于把“用户确认过”这件事写成了假的。

同一时刻可以从多台设备收到请求；请求条逐条呈现，各自独立接受或拒绝。

## 5. 流程状态与退出

| 状态 | 谁看到 | 主内容 | 允许操作 |
| --- | --- | --- | --- |
| 未开始 | A | 附近设备列表 | 扫描、点某一行的“配对” |
| 等待接受 | A | 目标名称、**六位数码**、“等待对方确认” | 收起（只收起视图，请求仍在对方屏幕上） |
| 被请求 | B | 发起方名称、完整 ID、地址、**同一组六位数码**、接受/拒绝 | 接受、拒绝（也可不理，到期失效） |
| paired | 双方 | 对方名称、已配对 | 完成，回到列表 |
| 被拒绝 | A | 对方拒绝了这台设备的请求 | 重新发起（对同一台设备） |
| 超时 | 双方 | 请求已过期 | 重新发起 |
| 失败 | 发起方 | 错误原因（对方不在附近、本机没有身份） | 修正后重试 |

**取消只在被请求的一方存在**（接受 / 拒绝）；发起方没有“取消”，因为请求一旦发出，
决定权就在对方屏幕上——本机只能停止显示那组数码，不能替对方收回。这一点与旧流程不同：
旧的“等待”是本机生成的一个任务，所以本机能取消它。

关闭设备页不结束任何进行中的请求——重新进来时，等待中的数码仍在，未被处理的请求仍在请求条里。

配对在 A 这边由一个后台线程完成：它把请求发出去，然后在对方接受时把记录写下来。
因此**列表不会自己跳**，而是等待区块存在期间每三秒重读一次设备列表，直到目标变成已配对或窗口结束。

关闭流程只关闭视图；若任务在继续，设备页保留紧凑“配对进行中”入口，可返回当前任务。
如果用户要结束任务，点击明确的“取消配对过程”，等待内核结束；“取消配对过程”和“取消已建立的配对”文案必须区分。
当前 `requestId/peerId/phase` 来自 store，不用 Modal 开关推导任务是否存在。

## 6. 文案、安全与长内容

**接受请求的那一侧，安全提醒就在确认条里**：对方完整 ID、名称、“通过局域网发现找到，发现不能证明它是谁”。
不放进 tooltip——一个人在接受之前就得读到它，而不是接受之后才去查。
日常设备页不重复整段协议教程。

ID/地址可辅助辨认，**不得标成“已验证”**；同名设备仍须有完整 ID 区分。
**配对过程不产生也不读取任何需要用户搬运的文本**，因此没有“凭证不写 URL、不发日志”这一类要求要守——
被拒绝的请求、超时、失败原因都只在界面里显示，不落成需要保管的东西。

## 7. 取消配对

从已配对设备更多菜单末尾进入，确认框写明目标、取消后的连接影响；不把它放在默认行最显眼的位置。
取消成功等待真实状态更新；失败保留配对状态与原因。不能自动删除插件、历史、接收文件或其他设备的配置。
现有 `devices_forget` 已撤销该发送设备的自动接收偏好，确认中应如实说明；这是内核已有契约，UI 不再额外执行第二次清理。不能由此推断其他权限、插件或历史也会删除。

## 8. 验收

无设备、只有已配对、只有附近设备、混合列表、同名设备、长 ID；扫描中/结束/取消/失败。

**配对要验的是两侧各自的视角**：

- **发起侧**：点“配对”先出确认，不点不发出；等待中该行不可重复发起；取消后行回到未配对；
  被拒绝与超时各自给出不同的话。
- **被请求侧**：确认条出现时不阻塞页面其余部分；接受后并入已配对；拒绝后请求结束；
  不理会的请求**不会自动消失**，而是等到期后自己结束。
- **两个请求同时到达**：两条确认条各自独立，接受一条不能连带处理另一条。

重点验证关闭后重入（等待中的行仍在等待，未处理的请求仍在确认条里）、换页后回到进行中任务、
取消中重复点击、IPC 失败，以及**同一台设备不能被配对两次**。

真实双设备握手需 Native 验证；纯浏览器假内核只能证明界面流程与调用参数。
