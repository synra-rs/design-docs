# 00 · 专业软件的完成度标准

> 2026-10-29 用户澄清：目标是让 Synra 有专业软件的感觉，解决当前类似 Demo 的观感。
> Folo 是参考对象；列表、卡片、分栏、Drawer、hover 都是按需使用的手段，不是必须照搬的页面模板。
> 本文是本目录的目标与评判入口，具体页面方案据此取舍；不改变组件库与宿主边界。

## 1. 专业感要体现在哪里

用户打开后，能迅速理解当前情况、知道该做什么，并相信每个操作都有明确且可靠的结果。
即使只有一个设备、两个插件、没有活动，也应像一款完整产品；不能靠填满数据、增加统计面板或隐藏所有细节来制造观感。

| 维度 | 目标 | 典型的 Demo 感来源 |
| --- | --- | --- |
| 页面目的 | 每页有清楚的关注点，常用信息自然先被看到 | 把已实现的接口与组件逐项堆在页面上 |
| 构图 | 页面宽度、对齐、留白与信息量匹配 | 大屏中间一条窄表单，或少量内容被拉成巨大的空面板 |
| 视觉秩序 | 字号、色彩、间距、控件尺寸有稳定的层次 | 标题、说明、标签、按钮各自成立，放在一起缺少整体关系 |
| 操作语义 | 主要动作明确，低频管理有稳定位置 | 每个功能都一个常驻按钮，或为了干净把动作全部藏起来 |
| 状态表达 | 在线、启用、运行中、待授权、失败各自准确 | 用多个标签解释同一个状态，或用“已启用”代替“正在运行” |
| 流程完整 | 开始、等待、取消、失败、重试、完成都可理解 | 只能证明按钮能调用接口，后续要靠控制台确认 |
| 环境适配 | 最小窗口、宽屏、触摸、缩放和两种语言都自然 | 只在开发者自己的窗口尺寸下看起来正常 |
| 使用节奏 | 内容与焦点稳定，反馈及时，返回后能继续操作 | 进度更新导致跳行、弹层乱叠、成功后不知道下一步 |

这些维度共同决定完成度；换成列表、减少按钮或统一圆角，单独都不能证明目标达成。

## 2. 当前问题的设计解释

以下判断基于 [02 的本轮截图和审查](./02-current-ui-audit.md)，不是新增一次审查或实现结果：

- 首页主要是状态展示，却让空插图、大连接面和重复说明成为视觉中心，真实内容失去优先级。
- 插件页把安装、搜索、已安装、权限和审计顺着实现顺序摆出来，缺少用户任务之间的组织。
- 设备页在用户还没开始配对时就展示完整教程，正常设备管理也像协议演示界面。
- 设置页虽然收起了高级内容，但分类、信息优先级、错误作用域与控件关系仍需要整体整理。
- 单个组件能用，页面之间的密度、主动作、反馈和技术信息显示方式还没有形成稳定约定。

重点是重新建立页面关系与使用流程，保留需要的信息；不能把“降低文字对比度”当成完成页面设计。

## 3. 先确定任务，再选表现形式

| 页面任务 | 可选形式 | 选择依据 |
| --- | --- | --- |
| 少量设备，重视辨认与连接关系 | 设备面板、分组卡片、简洁行 | 名称、状态、关系与操作能否自然组合，不强制改为列表 |
| 多个同类插件，需要快速比较/管理 | 紧凑列表、插件卡片/网格 | 数量、描述长度、高频操作与窗口宽度；正常项不全展开表单 |
| 首页状态与当前活动 | 简洁概览、少量分区、活动行 | 首屏重心与真实信息量，不强制变成时间线或数据仪表盘 |
| 调整少量偏好 | 直接分组设置行 | 能一眼找到就不必再增加分类与搜索 |
| 较多管理设置 | 分类页面、导航分组、局部折叠 | 缩短查找路径，不以减少页面高度为唯一依据 |
| 管理单个对象 | 就地展开、独立页面、Drawer、宽屏详情 | 信息量、操作频率、是否需要对照；不统一规定必须开 Drawer |

用现有能力选择最合适的形式；如果原页面结构经过整理已经自然，就保留它。
新结构必须说明它解决的具体问题；“Folo 是这样做的”本身不能作为改结构的理由。

## 4. 精致交互的适用边界

hover 可用于完整名称、准确时间、少量辅助动作和只读预览；让熟练用户更快，不增加初次使用的猜测。
菜单适合低频管理；详情适合较完整的属性和操作；折叠适合偶尔阅读的细节。
主要动作、必要状态、安全影响、错误恢复仍要在当下可见；若收起以后更难理解，应该保持展示或重新组织内容。

同一软件里，相同操作应出现在可预期的位置，状态色、反馈与确认方式保持一致。
不追求每个页面都出现 tooltip、弹出卡或动画；没有交互必要时，稳定且安静的展示就是合适的设计。

## 5. 内容与产品语言

宿主默认使用面向用户的名称与状态，技术字段在排查、核对身份、复制标识时完整可达。
用户已允许测试展示数据；插件 ID、trace 和“已接收/已完成”可以作为真实结构的示例，不要求删除或遮盖。
演示数据也必须遵守正式信息层级，不能把字段名、原始 DTO、调试按钮作为页面骨架；Native 不支持的能力不能用假成功填补。

说明只保留能帮助当前判断的内容，必要的说明可清楚展示；不以字数越少、颜色越淡为美观标准。
错误告诉用户发生了什么、影响是什么、可以做什么；成功反馈让用户知道结果和下一步，不能要求查看日志才能确认。

## 6. 实施顺序与评审

先统一四页的页面宽度、头部、排版、对齐、控件密度和状态反馈，再针对确实过载的部分调整结构。
对每个页面检查初始空白、正常少量内容、繁忙、错误和窄屏；以完整使用过程评审，不只评一张内容充足的漂亮截图。
后续视觉目标须在现有组件库和主题内形成，参考 Folo 的克制与连贯，但保留适合 Synra 的页面组织。

验收时至少能回答：

1. 默认画面的视觉重心是否符合这页的用途？
2. 少量内容和空状态是否仍像完整产品，而非等待填充的模板？
3. 同类控件、状态与动作在四页之间是否一致？
4. 用户能否不看介绍长文或控制台就完成常用任务？
5. 等待、失败、取消、重试与完成是否构成完整流程？
6. 收起内容是否真的减少干扰，同时保留发现和操作路径？
7. 换窗口尺寸、语言或输入方式后，整体关系是否仍成立？

列表数量、hover 数量、Drawer 使用率都不是验收指标；页面整体完成度与真实使用质量才是。
